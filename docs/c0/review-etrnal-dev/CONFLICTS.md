## 1. 甲档：架构级

### C01 信任模型：Hub 能不能看到明文

| | 内容 |
| --- | --- |
| `etrnal-dev` | 第 3 节架构：Hub（微信云托管 + MySQL 5.7）保存账号、设备目录、会议状态、任务、审批、事件。Hub 是受信任的中转，能看到会议正文，也能向已配对设备下发任务 |
| C0 | ADR 0014 与 `remote-control.md` R7、§4、§5.1：群聊、私信、小文档只有可信设备能解密；官方中转只见密文。用 Ed25519 签名 + X25519 封装，libsodium |
| 差别 | ① Hub 被攻破或运营方越权时，会议内容全部可读。② Hub 可以伪造任务下发给执行设备。执行端的本机授权只能限制目录和 Agent，管不了任务内容是否出自用户，所以伪造的任务等于在授权目录里执行代码 |

选项：

- **a**：首版采用受信 Hub，但所有改变执行状态的命令都要带发起设备签名，执行端验签。具体命令包括派发、继续、补充、停止、批准，签名用 Ed25519，即 ADR 0014 的 L1 部分。内容加密延后，在设置和隐私说明里明确告知「Hub 能看到会议内容」。ADR 0014 改为「部分延期」，并写一条新 ADR（0017）。粗估 M。
- **b**：在 `etrnal-dev` 的 Hub 上补完整端到端加密。代价是 Hub 的服务端快照、去重、计划投影都依赖明文，要改成客户端投影，等于重做 Hub 的大半。粗估 XL。
- **c**：采用 Hub 现状，签名和加密都延后。

**建议 a。** 首版设备少、验收在内部进行，内容加密可以延后；但「Hub 能远程让我的电脑执行代码」这个风险不应进首版，签名能用较小代价消掉它。

### C02 Hub 上数据的保存期限（D12）

| | 内容 |
| --- | --- |
| `etrnal-dev` | 第 5.3 节：已接任务的长期业务记录不能只寄存在定期清理的传输 journal 里。Hub 长期保存会议、任务和事件；文档里没有写保留期限 |
| C0 | D12：中转离线信箱保留 30 天。前提是中转只存密文、只做转发 |
| 差别 | 如果 C01 选 a 或 c，Hub 就从「30 天密文信箱」变成「长期保存明文会议记录的服务」，D12 的前提不成立 |

选项：

- **a**：会议和任务记录在 Hub 长期保存；用户可以删除会议，删除后 Hub 同步删除。投递队列保留 30 天（沿用 D12）。
- **b**：会议正文在 Hub 只保留 N 天，长期记录只存在各设备本地。
- **c**：维持 D12，Hub 上所有数据统一 30 天。

**建议 a。** b 和 c 会让「协调设备离线、另一台设备恢复」的场景丢数据，与 `etrnal-dev` 第 5.3 节冲突。

### C03 执行端的运行底座

| | 内容 |
| --- | --- |
| `etrnal-dev` | 执行端由 Python 接收组件 `services/remote/device/station_codex.py` 直接驱动 Codex app-server：<br>• 版本写死为 `0.144.1`（`:142`）；<br>• 沙箱用 `read-only` / `workspace-write`，审批用 `untrusted`（`:90`、`:157`）；<br>• 已有对话接续在 `codex_shared_service.py`；<br>• 安装包内置 Python 运行时 |
| C0 | 只保留一个运行底座，即 TS 侧现有 adapter（D14、ADR 0016），同样走 Codex app-server（`electron/backends/codex-app-server-transport.ts`）。A-14 已在 0.156.1 上实测：`untrusted` 不再可用，`workspace-write` 会让工作区写入绕过宿主。授权映射改为 `read-only + on-request`，并按 G4 做事后 hash 比对；版本门按 G8 改为区间 |
| 差别 | 两套驱动 Codex 的代码，授权语义不一致。按 `etrnal-dev` 现状合入后，跨设备任务会在 Codex 0.156.1 上全部被拒（R1 的阻断项 B2）；即使放开版本，也会重新引入 A-14 已否决的写入绕过 |

选项：

- **a**：执行端改成调用 TS 侧 adapter，也就是 A-14–A-20 修好的那套。Python 接收组件只保留接收、持久化、核对和守护进程隔离（guardian）。已有对话接续作为 adapter 的新能力补上。粗估 L。
- **b**：保留 Python 执行路径，把 A-14（授权映射）、G4（hash 比对）、G8（版本区间）移植过去，并让它跑 B04 的 S1–S10 一票否决场景。之后两套代码要长期同步修。粗估 M，但每次 Codex 升级都要改两处。
- **c**：两套并存，不对齐。

**建议 a。** 「单一运行底座」是 D14 的核心理由。b 的短期成本低，但 A-14–A-20 这类问题以后会在两边各出现一次。

### C04 已有 Codex 对话的远程接续，以及完全访问权限

| | 内容 |
| --- | --- |
| `etrnal-dev` | 第 2.3 节、ADR 0002 / 0010、Q89–Q90：<br>• 可以点名另一台电脑上已有的 Codex 桌面对话，保留它原来的模型、审批设置和权限；<br>• 原对话是完全访问的，经 B 本机明确授权后也可以远程接续 |
| C0 | 没有这项功能。C0 的授权不变量是「授权留在宿主手里」：ADR 0016、A-14 只允许 `read-only + on-request`，获批命令还要按 G4 检查是否越界 |
| 差别 | 完全访问或 `workspace-write` 的已有对话一旦被远程驱动，写入就不经过宿主授权，G4 的事后检测也挂不上 |

选项：

- **a**：首版做远程接续，但只接受权限不超过本机项目授权的对话（`read-only` / `on-request`）。完全访问的对话显示「需要在本机桌面继续」。
- **b**：按 `etrnal-dev` 原样，本机明确授权后可以远程接续完全访问的对话。
- **c**：首版不做已有对话接续，只做新任务派发。

**建议 a。** 它推翻了 `etrnal-dev` 第 2.3 节第 4 条，需要转告作者。

### C05 支持哪些平台，双机验收怎么做

| | 内容 |
| --- | --- |
| `etrnal-dev` | 首轮实机验收是 Windows ↔ Windows（第 1 节、10.2）。执行端的 guardian 只实现了 Windows（WindowsJob）和 Linux（LinuxTaskTree）；macOS 直接拒绝执行（`station_codex.py:100-104`） |
| C0 | 双机验收用 Mac + N5095（Windows），两端都要能执行（X8、B04 证据） |
| 差别 | 按现状，Mac 只能当协调设备，不能接任务 |

选项：

- **a**：首轮按 `etrnal-dev`：需要第二台 Windows，Mac 不参与执行验收。
- **b**：先给 guardian 补 macOS 实现（进程组 + 进程树核对），再做 Mac ↔ N5095 双向验收。粗估 M。
- **c**：首轮 Mac 当协调设备、N5095 执行，单向验收；macOS 执行端作为后续卡，即选项 b，排在首轮之后。

**建议 c。** 现有硬件就能跑，又不阻塞首轮。
