# Paseo 与 Multica：对 AhaStudio 定位的冲击（2026-10-03）

> 研究对象：用户所写“mutica”按 **Multica**（`multica-ai/multica`）理解。核对的是 Paseo `d831c7b`、Multica `b2561aa` 的公开源码及随仓文档；未安装、启动或做端到端体验测试。下文“已实现”指存在产品文档和相应代码路径，不代表可靠性已经独立验证。“未见”仅指本次检索范围，不能证明绝对不存在。AhaStudio 一栏是[当前产品定义](../../CONTEXT.md)和[策略稿](./openclaw-aha-strategy.md)，不是已交付能力。

## 一句话判断

Paseo 已占据“把现有 Coding CLI 放到手机与桌面、加语音控制”的位置；Multica 已占据“把 Agent 当团队成员，围绕 Issue 分派、追踪、异步处理”的位置。AhaStudio 若仍用“多 CLI + 手机遥控 + 语音 + Agent 看板”作核心宣传，将被直接比较为后来者。更有力的主张是：**用户说出或在会议中形成目标后，系统把目标澄清为可授权的任务，组织原生 Harness 执行，只为真实决策打扰用户，并用独立证据交付可验收结果。** 这是当前 AhaStudio 的设计机会，还不是已验证的市场护城河。[AhaStudio 策略](./openclaw-aha-strategy.md)

## 对产品策略的直接修正

1. **不要以功能清单发布。** “支持 N 个 CLI、手机、语音、看板、Inbox、自动验证循环”已是竞品交集。发布演示必须是同一真实任务完整经过：说/开会 → 预调查与少量质询 → 确认 Task Charter → 原生 Harness 执行 → 异步 Decision Inbox → 冻结验收规则下的证据交付。每一步都能点击查看原始来源。[AhaStudio 策略](./openclaw-aha-strategy.md)
2. **选一个足够窄的首发楔子。** 推荐个人开发者/小团队的“正在多个 CLI 中做同一项目、经常离开电脑”的场景。先把 Codex + Claude 的本地会话发现、任务归并、AhaBar 注意力分流和手机决策做好。Kimi、OpenCode、Pi 随适配器成熟加入。Multica 已占团队 Issue 工作台，Paseo 已占远程 CLI 控制；首发不宜同时铺 26 个浅适配。
3. **把 AhaTalk 绑定任务成果。** Paseo 的语音已经能驱动 Agent；AhaTalk 应提供中文和专业词库、口语结构化、澄清卡、会议决定转任务及可回看依据。衡量“语音任务一次启动成功率、澄清轮数、误批准率、最后交付接受率”，不只衡量转写字错率。
4. **权限保真是工程门槛。** 每个 Harness adapter 都要声明可否读取历史、实时事件、steer、权限桥接、续跑、用量、成本和产物；功能入口依声明渐进开放。对跳过批准的 CLI，不应套一层视觉上的中高风险确认后仍允许其自行越界。
5. **Autonomous Loop 后置但从第一天埋证据模型。** Task/Run/Evaluation Contract/Decision/Artifact/Evidence/Cost/Permission 要有稳定关联。先证明在可计算验收任务上“达标即停”比普通 Agent 重试更可靠，再把 Work Recipe 与独立 Verifier 开给社区贡献。
6. **设备承接软件价值。** AhaBar 是任务注意力视图；AhaKey 把低/中/高风险确认做成可信触觉操作；AhaStation 保持任务可恢复的跨设备连续性。软件必须独立完整可用，硬件改善随身感、反馈和切换成本。这比宣称另一个多 Agent 执行器更符合现有[AhaStudio 定义](../../CONTEXT.md)。

## 需要验证的竞争假设

- Paseo 的会话导入在真实 Codex/Claude 不同版本、无 CLI 登录、跨目录时的成功率和信息保真；代码路径存在，但不能据此推断用户迁移顺畅。
- Multica Squad 在并行 Worker 多意见冲突时是否真正保留、升级原始风险；文档有 leader 路由与 Inbox，未见 AhaStudio 所定义的 Mandatory Escalation 契约。
- AhaStudio 用户是否愿意在任务开始时确认一张简短 Task Charter，换取执行中更少被打断。这个设计必须经可用性测试，不能仅凭概念推断。
- 独立 Verifier 是否明显提高接受率，并能把额外 Token/时间成本控制在用户愿付范围内；要按任务类型公开实测。
