### Orca 结构化 Orchestration（Experimental）

Orca 的 Run 是持久 namespace 和 coordinator inbox，本身**不调度**；Task 有依赖和状态；Dispatch 是一次具体执行尝试；消息有 `worker_done`、`escalation`、`question`、`heartbeat` 等类型；gate 可以阻塞 Task。CLI 可在当前或新子 worktree 上 `worker-start`，也可指定另一执行主机，worker 通过 `ask` 向协调者提问，完成报告必须携带 Task/Dispatch ID，避免旧尝试错误结案。[对象定义](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/cli/orchestration.mdx#L23-L47) · [跨主机派工](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/cli/orchestration.mdx#L89-L104) · [Worker 合同与 gate](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/cli/orchestration.mdx#L131-L164)

源码中已存在 dispatch 生命周期、消息投递、联邦同步、gate 与 worker transcript 等持久结构；Task 状态为 pending/ready/dispatched/completed/failed/blocked，dispatch 还有 stale/rejected 防护。`reblockTasksWithPendingGates` 确保未处理 gate 不被自动放行。[类型](https://github.com/stablyai/orca/blob/v1.4.218/src/main/runtime/orchestration/types.ts#L3-L40) · [gate 实现](https://github.com/stablyai/orca/blob/v1.4.218/src/main/runtime/orchestration/coordinator-decision-gates.ts#L52-L61)

但这层当前更像**开发者通过 CLI/skill 驱动的监督式派工底座**：用户或协调 Agent 创建 Run、Task、worker，处理消息与 gate。官方文档明确标记 Experimental，旧 `orchestration run`/`run-stop` 已无效。没有足够证据称其已实现 Aha 所定义的 Task Charter、Evaluation Contract、独立验证、风险分级 Decision Inbox 或全局用户注意力治理。[实验标识与旧命令](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/cli/orchestration.mdx#L8-L20) · [Aha 约束](/Users/heartline/Documents/Codex/ahakey-studio-community/CONTEXT.md:15)

## 4. 权限、验证与交付：真正需要拉开的距离

Orca 为新启动的多种 CLI **预填绕过逐工具批准的参数**，包括 Claude `--dangerously-skip-permissions`、Codex `--dangerously-bypass-approvals-and-sandbox`；官方特别说明 worktree 是隔离 checkout，**不是安全沙箱**，用户可切换全局 Manual 或逐 Agent 改参数。这与 Aha“默认观察，交互由用户开启，自动调度按项目授权，每个任务明确 Operating Envelope；按风险分级确认”的原则有实质差异。Aha 应坚持这条产品边界，并把启动前的预期权限显示清楚。[Orca 默认权限](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/agents/supported.mdx#L8-L23) · [Aha 权限](/Users/heartline/Documents/Codex/ahakey-studio-community/CONTEXT.md:259) · [Aha 任务澄清](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:131)

Orca 的 Review 流程已具备 Diff、行级注释、提交/推送/PR，支持同一问题让多个 Agent 各跑一个分支然后人工挑选。结构化 worker 结束要报告 `worker_done`，gate 提供阻塞点；这些是成熟的**代码产物审阅和派工原语**。但从所查官方文档与核心源码，尚无证据表明 v1.4.218 将独立可重复 Evaluation Contract、版本冻结、验收证据、默认“达到可接受标准即停”、Verifier 冲突升级整合为系统级自动交付合同。Aha 的竞争单位应是“用户接受的一次有效交付”，不是并行 Agent 数量。[Orca 并行配方](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/recipes/parallel-agents.mdx#L1-L23) · [Orca Worktree Review 生命周期](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/model/worktrees.mdx#L17-L28) · [Aha Evaluation Contract](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:98) · [Aha 北极星](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:369)

Orca 既有通知与 Dashboard 的单位是 Agent 工作/空闲/待输入；Orchestration 中的 `ask` 和 gate 是 Worker/Coordinator 或 Task 内的同步决策机制。Aha 的 Decision Inbox 进一步规定：Host Agent 独占用户注意力入口，合并普通问题，保留 Worker 原始警告，重大风险必须升级；日历 Decision Link 只打开确认界面，链接本身不批准；IM 只可批准一次性低风险动作。这是用户注意力与安全模型，不应做成 Orca 状态看板的另一层皮肤。[Orca 通知](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/notifications.mdx#L5-L27) · [Orca gate](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/cli/orchestration.mdx#L131-L164) · [Aha Decision Inbox](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:143)

## 5. 可借鉴的实现与路线调整

1. **先建立适配能力等级表。** Orca 对“任意 CLI 可启动”与“状态、Hook、用量、Chat UI、恢复是否可用”有明确深浅差别。Aha 的 Adapter 应公开 observe/start/resume/steer/interrupt、会话所有权、Hook 事件、Usage、批准桥接和版本兼容，避免营销中把能启动误说成能完整管理。[Orca 支持矩阵](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/agents/supported.mdx#L8-L65) · [Aha Adapter 契约](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:199)
2. **把“历史扫描 → 实时连接”做成可见的两阶段。** Orca 的历史读取与实时状态是两条路径，Aha 首启可先展示有来源和置信度的历史任务，再按需连接 Hook；连接页要展示目标文件、精确 Diff、备份、恢复及事件测试。[Orca 历史](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/agents/session-history.mdx#L54-L56) · [Orca 状态](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/model/agents-sessions.mdx#L8-L26) · [Aha P0](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:301)
3. **吸收 Run/Task/Dispatch 的持久身份与故障护栏。** 尤其任务尝试 ID、防过期完成报告、未确认 gate 不能自行放行、主机拥有执行状态、移动端只是投影。这些让多 Agent 真实可靠，但 Aha 的用户 Task/Charter/Decision/Evidence 应保持更高一层语义。[Orca Orchestration 类型](https://github.com/stablyai/orca/blob/v1.4.218/src/main/runtime/orchestration/types.ts#L21-L40) · [Orca gate 不自动解决](https://github.com/stablyai/orca/blob/v1.4.218/src/main/runtime/orchestration/coordinator-decision-gates.ts#L52-L61) · [Orca 状态权威](https://github.com/stablyai/orca/blob/v1.4.218/docs/reference/agent-status-store.md#L45-L61)
4. **P0/P1 的展示要调整。** 单独发布“支持几十个 CLI、手机控制、语音听写、额度雷达”已经不足以区分。首个可传播演示应是：已有会话自动归成真实任务 → 用户说目标，系统生成 Task Charter 并一次确认 → 原生 CLI 工作 → AhaBar 只提示一项重要决策 → 低风险远程确认/中高风险可信端确认 → 证据和 Diff 交付。这个闭环对非键盘用户完整可用，AhaKey 提供更直接的交互与情绪价值。[Orca 既有功能](https://github.com/stablyai/orca/blob/v1.4.218/README.md#L34-L188) · [Aha P0–P1](/Users/heartline/Documents/Codex/ahakey-studio-community/docs/research/openclaw-aha-strategy.md:301)
