# AhaStudio AME 产品决策与待讨论问题

更新日期：2026-10-22。面向产品、设计、软件与硬件开发协作者。

AhaStudio 定位为 Agent Meeting Environment（AME）。用户主要与一个长期助理交流，由助理主持会议、按需组织 Agent、把讨论转成任务，并持续推进到有证据的交付。AhaStation 是专门承载这支 Agent 团队的随身第二台电脑，首发以 Windows 为主。

本文汇总本轮完整讨论，区分已确认决定、待讨论问题和待验证事项。已确认是产品规则，不代表代码已经实现。后续继续 grilling 时，优先处理本文的问题编号，避免重复询问已经确定的原则。

## 阅读与更新规则

- **已确认**：用户在本轮直接提出或明确接受；各节 D 编号用于追踪。
- **纪要方向**：所提供会议纪要里的阶段规划或建议，尚不能视为已完成的能力。
- **待讨论**：需要用户或团队做产品取舍。
- **待验证**：需要源码、SDK、样机或真实运行证据；应先调查，不把事实问题反复抛给用户。
- 新决定补到对应 D 条目，并把相关 Q 条目更新为已解决；保留变更依据。原则改变时明确替代旧决定，避免并存两套规则。

本文是本轮 AME 方向的讨论基线。既有代码事实、历史测试报告仍保留在原文件中；本次不修改产品代码，也不将旧 WBS 的工作包标为完成。

## 产品定位与首发范围

| 编号 | 已确认决定 | 边界 |
| --- | --- | --- |
| D01 | AhaStudio 的产品类别为 **Agent Meeting Environment** | 重点是交流、会议、决定与工作推进，不以终端数量、并行 Agent 数量作为主要价值 |
| D02 | AhaStation 是硬件，AhaStudio 是软件 | 对外方向为 **Your agent computer, anywhere**；软件也可以运行在用户已有电脑上 |
| D03 | AhaStation 是专门承载 Agent 团队的第二台电脑 | 可随身使用、接外屏独立工作；首发不以全面替代用户已有主力电脑作为默认承诺 |
| D04 | 用户不必擅长 coding，也能通过安排、讨论、取舍和验收推进项目 | Agent 是用户的团队；软件应减少管理每个 Worker 和每一步模型的负担 |
| D05 | 首发聚焦项目与创造工作 | 支持研发、设计讨论、资料研究、文档和交付；通用问题可以分析，邮件、日历、订酒店等完整事务执行后续按场景扩展 |
| D06 | 首个验收项目为 AhaStudio 自身，首项需求确定为看板记住最近项目筛选并在刷新或重启后恢复，Issue 由用户之后创建。先 A 读取 Issue、语音澄清、生成带来源和条件的 TODO，确认且重启仍在，暂不派工；B 再实际修改、检查和交付 | 首次公开可用门槛为双向跨设备 B，手动指定设备，经 GitHub 交接并回传成果；主持固定版本与分支候选版分开；首次筛选仍全部，旧项目失效回到全部，不新增跨端偏好同步；Issue 链接、细化样例及体验者待补 |
| D07 | 首批项目都基于 GitHub 协同 | 跨设备执行先采用 GitHub 项目；任意文件夹同步和其他资源交接后续扩展 |
| D08 | 首发提供内置看板、GitHub Issue 读取与可选结果回写；回写可由用户设置或自然语言明确要求 | 默认不自动关闭 Issue；关闭需明确授权，回写、关闭与合并代码分别处理；设置粒度及回写内容待 Q12 细化，其他看板数据后续扩展 |
| D09 | 用户连接自己的 AI 服务，项目可获准使用多个服务各自的额度；默认按职能角色与任务复杂度选模型，支持手动设置优先级、统一优先使用某服务及达到阈值后的切换顺序 | 自动切换仅限已连接、已授权且满足能力、权限、数据处理与预算要求的服务；保留任务产物与边界并记录切换，无合格服务则暂停询问；角色身份保持，底层服务可查；不自动新增付费服务、充值或扩大授权；AI 凭据与 Aha 账号分开，不承诺硬件附带模型额度 |
| D10 | AhaStation 首发以 Windows 为主；首次公开可用版本必须通过 Windows x64＋macOS Apple Silicon 双向跨设备 B：Windows 发起到 macOS 执行、macOS 发起到 Windows 执行均验收；软硬件分别发布，软件先验证闭环、完整功能验收后正式发布，整机通过硬件测试后交付 | 两端选符合目标平台能力的任务和 Harness，不承诺全部能力等价；Intel Mac、Windows ARM 和 Linux 后置；具体日期另定，不因分别发布缩减完整软件首发范围 |

**人群与获客的当前建议，尚待验证：** 已有 Mac mini 等固定 Agent 主机的用户适合先体验 AhaStudio；正在购买第二台电脑、又有家与办公室等多地点需求的人，更可能成为 AhaStation 首批硬件买家。“是否需要把实际个人项目环境带到多个地点”比“有没有 Mac mini”更能解释硬件购买理由。尚未冻结首批招募配额、价格、获客渠道和市场规模。

## 助理与团队组织

| 编号 | 已确认决定 | 边界 |
| --- | --- | --- |
| D11 | 用户主要与一个长期助理交互，助理始终担任会议 Host | 助理理解用户、定位项目、组织协作、收敛决定并对用户汇报 |
| D12 | 默认不要求每个项目设置专门项目经理；普通项目由助理兼任项目经理，直接协调职能负责人，复杂项目再委派独立项目经理 | 独立项目经理协调职能负责人并向助理汇报，用户始终主要与助理交流；保持唯一项目协调责任，不因团队职能层级而强制每项目新增经理 |
| D13 | 每个项目有独立、持久记录；已确认需求、架构约束、设计方案和验收标准进入项目正式文档并由 Git 管理；完整沟通、临时讨论、个人偏好和授权记录保存在 AhaStudio | 正式文档关联讨论来源与版本，优先更新已有规范，避免重复文档；完整聊天不自动提交仓库；项目知识不只存在某个子 Agent 会话，换 Agent 或工具仍能接续 |
| D14 | 专家以“职能名称＋名字”展示，并作为相应职能负责人；覆盖产品、设计、运营、前端、后端、测试等职能。职能负责人可为不同项目派不同执行子 Agent，结果同步回负责人 | 项目经理按 D12 由助理兼任或独立委派，协调职能负责人并汇总进展；设备协调者管理本机执行；职能身份、模型与会话分别处理，不要求所有负责人始终运行模型进程 |
| D15 | 默认会议为用户与助理双人会议，其他 Agent 按需加入；首发每位专家都有独立音色，与其职能和名字对应；同一时间仅一位 Agent 语音发言，由助理 Host 安排顺序 | 专家补充或异议先向 Host 示意，再受邀发言，用户也可直接点名；明确风险立即提交警报并暂停受影响任务，不等待发言；用户语音键可打断播报但不自动停止后台任务。不要求每次语音固定三人入会，不能降为所有专家共用一种音色；具体 SDK、声音资源和调度实现仍需验证 |
| D16 | 成员可以阻止明确越权、可能破坏数据或无法满足既定验收条件的相关执行 | 立即报告 Host；暂停受影响任务及其依赖，其他独立任务继续；普通方案分歧由 Host 核实协调 |
| D17 | 同一项目保持唯一的逻辑协调责任，不出现相互独立的正式计划 | 先前“每个项目必须有独立经理”的设想已被 D12 替代；唯一责任不等于必须常驻一个经理进程 |
| D18 | 助理根据 Demo 或工程项目等成果用途调整推进方式和成员划分；Demo 可精简成员并兼任部分职能，工程项目按模块与风险细分 | 能判断时直接采用，不明确时简短询问；具体编制由助理按需组织，不强制用户逐个配置职业或角色人格；两种项目都必须独立验证，具体标准仍需定义 |

严肃项目可以更重边界、测试、版本与回退；兴趣项目可以更重探索与原型。工作方式变化不取消费用、权限、不可逆动作与验收规则。首发角色采用稳定头像与轻量状态动效，突出说话、录音、思考、执行和待决定状态；用户可改名字和头像，各专家独立音色。手持与外屏优先呈现任务、材料和成果，复杂 3D 及口型同步后置。人格表达、具体音色配置与发言长度通过 Q27 的原型继续设计。

**组织关系：** 普通项目由助理兼任项目经理、协调职能负责人；复杂项目可委派独立项目经理，再由助理统一面向用户。职能负责人按项目派执行子 Agent 并接收结果。跨项目专业沉淀与各项目上下文边界仍需 Q23 细化。D16 的风险暂停与直接上报责任继续适用，不因逐级汇总而延迟必要升级。

**专家邀请：** Host 默认可直接邀请项目内已有专家入会，简短说明邀请原因，无需逐次弹窗征求同意；用户可说“先别叫人”阻止邀请，也可手动邀请。邀请不自动扩大权限，新增付费服务或扩大项目数据访问范围仍按项目权限规则处理。

**专家按需调用：** Host 持续承接对话，默认不在每轮对话调用所有专家模型；相关议题、用户点名或任务异常触发对应专家调用。用户要求“大家分别评估一下”时，再收集多方意见。界面“在会”不代表模型持续运行，也不表示专家已审阅每句话，必须区分在会状态与实际审阅记录。

**入会上下文：** 默认向专家提供当前议题、已确认目标与约束，以及相关原话、文档和任务版本的引用。专家可在已有权限内回查原始材料，发现信息缺失或冲突时明确提出；不能只依赖 Host 摘要，也不默认灌入全部聊天。其他项目的私有内容不自动带入。

**执行中的外部变更：** GitHub Issue 或项目文档变化时，自动发现并呈现与当前计划的差异。补充资料可直接参考；涉及目标、范围或验收变化时形成变更提案，由用户确认后修改计划，不直接覆盖正在执行的安排。继续执行可能造成错误时暂停受影响任务，其他独立任务继续；保留旧计划及其依据以追溯方向变化。

## 主动工作与任务生命周期

| 编号 | 已确认决定 | 边界 |
| --- | --- | --- |
| D19 | 助理具备主动推进、跟进、汇报和组织讨论能力 | 用户离开语音对话后，已授权工作继续；不是只有用户发问时才行动 |
| D20 | 普通进展进入群聊与看板并合并汇报，不逐条弹通知；团队可自行处理的问题先内部解决，需要用户决定、额度不足或无法继续时再提醒 | 明确越权或数据风险先暂停相关执行再通知；后台先提醒、选择后收听，可设专注时段与主动播报。汇报基于事件证据，未知先核实，不编造完成状态或百分比 |
| D21 | 默认事件触发，可通过对话约定定期简报与提醒偏好 | 例如“晚上汇报一次，其他时候只有卡住才找我”；具体限频与紧急等级待定 |
| D22 | 对话中自动创建、更新 TODO，不要求逐张卡片确认 | 创建记录不等于授权执行；助理可以先形成草稿与待讨论项 |
| D23 | 原计划与授权范围内的细化、分派可直接推进；所有权限模式均保留阶段计划确认，允许自然语言，不强制固定口令 | 明确请求确认且只有一个具体、带版本的安排时，“好”“可以”等确认该安排；介绍方案、多选项、换话题或识别不清时不直接开工；屏幕提供同一操作；完全访问确认阶段计划后，执行操作按 D58 免逐次批准 |
| D24 | 原范围内的返工修正直接推进 | 新增目标、明显增加费用或改变验收标准时，复述变化并重新确认；不因一句笼统反馈无限扩展工作 |
| D25 | 每个项目默认设置每周执行总额度，支持用户改为每月或每天，由项目经理按任务复杂度灵活分配；额度控制为主、时间控制为辅。按服务适配金额、可读的订阅额度或明确标注的 Token 等估算口径。每项可验收任务最多 3 轮“实现→独立复核”且包含首次，支持手动设置与对话调整 | 按 D12 由助理兼任或独立委派的项目经理统筹，不要求每项目新增经理；所有执行任务、Worker、重试与验证共享项目周期总额度，分配不等于提高总上限；未知额度不伪装精确余额，不同单位不直接相加。会议不限费用、不占执行时长，ASR／TTS 不计项目用量；重置时点、具体数值及辅助时间策略待定，原 30 分钟仅为历史初值 |
| D26 | 所有交付必须经过独立复核，开发后有明确验证环节；实现与复核使用独立会话，不强制不同模型，跨模型复核可配置 | 复核者读取原始需求、已确认条件、对应版本与产物，自行检查并提供证据，发现问题交回实现者；不能仅复述完成报告；验证随阶段计划授权，额外费用、生产操作、新权限另行确认 |
| D27 | 区分产物已生成、检查结果、待人工验证、用户验收；独立复核分为必须修复、非阻断建议、无法判断 | 必须修复阻止通过并返工；非阻断建议进入后续 TODO，不阻断达标交付；必验项无法判断时请专家或用户判断，不自动通过；复核不临时扩大需求，重要风险必须提出；检查通过不等于用户接受 |
| D28 | “接受结果”不自动合入代码 | “接受并合入”额外授权集成到指定分支；冲突暂停汇报；推送、部署、正式发布按各自授权处理 |
| D29 | 决策同时支持语音与屏幕点击 | 交付选项包含接受结果、接受并合入、继续修改、稍后处理；两种入口共用同一决定和授权状态，处理后各视图同步 |

需要确认时，自然语言绑定助理刚复述的具体阶段和版本，不能把任意肯定词当作通用批准。完全访问也保留阶段计划确认；默认模式的高风险确认、确认过期和多个请求仍由 Q07 细化。

| D32 | 共享区默认共享看板，可切换文档、网页、PDF、CLI 和成果；支持 Agent 按任务使用 computer use、tool、skill 执行操作与修改，不将共享区只读展示等同于 Agent 只能读取 | 首发 CLI 对用户只读展示命令、输出与错误，不支持用户直接接管；用户人工排查打开原工具或系统终端，Agent 可在授权范围执行命令。看内容不改变语音对象或自动授予操作权限；具体工具和格式兼容性仍须验证 |
| D33 | 助理主持时可主动展示相关内容 | 用户开始阅读、滚动或在支持的对象上编辑后，优先保持当前内容；助理需要展示其他内容时提示，用户可允许继续展示；首发不包含共享 CLI 内置接管 |

**GitHub 工作项映射：** 主工作项关联 GitHub Issue，详情中的职能及执行子任务默认在 AhaStudio 管理，不自动逐项创建 GitHub Issue。用户明确要求或项目设置开启后，再创建对应 Issue／子 Issue，仍遵循可选回写权限。具体 API 能力、关联去重与同步冲突需验证。

**甘特图时间语义：** 区分用户与助理确认的计划时间、随进展更新并明确标为估计的预计完成时间，以及真实开工、暂停和完成的实际时间。预计延期时说明原因并提出调整建议，不静默移动已确认的计划日期；未排期任务明确显示“未排期”，不编造日期。

**看板阶段与细分状态：** 默认大阶段为“待设计 → 待执行 → 执行中 → 测试中 → 已完成”。待设计用于通过 grill 明确产品、技术及 UX 方案；原建议的独立复核和待验收合并显示为测试中，但 D26、D27 的独立复核与用户验收记录仍须保留。任务在各阶段内以细分状态表达进展，例如阻塞、暂停、执行失败、状态未知、待接受、已提交、已合并发布；细分状态的适用阶段及提交、合并、发布的实际证据需明确定义，不能用显示标签代替真实结果。已完成按任务约定的交付终点判断：方案任务以方案验收为准，要求代码合并则必须完成合并，要求上线则必须完成发布；均保留独立验证和用户接受要求，不将所有任务统一要求合并或发布。

手持场景以简短对话、听汇报和处理决定为主。接屏后，主屏承载完整看板、文档、代码与成果，AhaStation 作为会议与助理陪伴副屏。跨屏迁移、焦点与音频规则尚待 Q18 细化。

**Agent 操作环境：** Agent 优先操作 AhaStudio 内置浏览器、文档工具、CLI 等，用户日常操作软件外的本机浏览器、文档工具等应用。Agent 需要查看或控制某台设备上 AhaStudio 外的软件时，必须取得用户对屏幕共享、界面控制等能力的授权；不能把进入项目或显示共享内容视作已获得外部桌面访问。授权明确设备、应用或屏幕以及仅查看或允许操作，默认只对本次任务有效；持续显示授权状态，用户随时可停止。项目完全访问不自动开启外部屏幕查看或控制，用户可另行设置长期允许。内置工具不等于操作系统权限沙箱，具体隔离能力需验证。

**设备授权引导与远程确认：** 软件安装引导时询问用户是否授权操作当前设备的其他应用，并引导完成相应屏幕查看、界面控制系统权限。设备能力授权与任务授权分开，安装时允许不等于批准所有后续任务；任务需要使用时请求具体确认，支持用户在当前可信设备上批准另一台设备的请求、拒绝或停止，请求标明目标设备、任务、应用及查看或控制范围。目标设备缺少必要系统权限、仍需现场处理系统弹窗时暂停并说明原因，不能将远程确认显示为已取得系统权限。两端具体安装或首次启动的系统授权路径需实测。

**浏览器与日常浏览数据：** 默认使用独立的 Agent 浏览器空间，用户可在其中登录网站，登录状态保存在当前设备，不自动跨设备复制。用户也可明确授权读取日常浏览的数据，或授权 Agent 操作其日常浏览器；读取数据与操作浏览器分别授权，不因允许其中一项自动获得另一项权限。未授权时不自动读取外部浏览器账号、Cookie 或历史。具体可读取的数据种类、范围及浏览器适配由实现验证，不将用户授权等同于已具备技术读取能力；外部浏览器操作沿用设备及任务授权规则。

**内置浏览器人工接手：** 首发支持用户在登录、验证码或其他需要亲自操作的场景直接接手内置浏览器。点击“接手操作”暂停 Agent 对该浏览器的操作，用户完成后点击“交还助理”，Agent 重新检查页面状态再继续，避免双方同时操作。用户已明确 CLI 不支持直接接管，浏览器接手能力不扩展到 CLI。

**文档人工接管：** 用户可接管文档编辑；接管期间 Agent 暂停修改该文档，等待用户完成并交还。交还后 Agent 先阅读用户的变更点，再基于最新内容继续修改，不沿用旧版本直接覆盖。此处暂停针对接管文档的修改，不等同于停止全部项目任务。首发具体文档格式与编辑器兼容性仍需验证，不能据此承诺所有格式均可直接编辑。

**主任务完成与子任务汇总：** 必需子任务完成后，主 Story／工作项仍需整体验证，达到约定交付终点并由用户接受后才进入已完成，不能仅凭子任务完成数量自动判定。非阻断优化建议转入后续任务，不拖住当前达标交付；用户无需逐个验收内部执行子任务，各项交付仍遵循独立复核要求。

**待设计收敛与开工门槛：** 当前工作项的目标及不做范围明确，必要的产品、技术、UX 决策已定，验收条件可检查，阻塞性疑问已解决且权限与预算明确后，助理主动收敛并请求开工确认。非阻塞细节记录为假设或后续问题，在授权范围内继续调查，不无限追问。复杂项目可先确认一个可执行阶段，无需一次设计完整个项目；本规则不取消 D23 的阶段计划确认。

**技术决策分工：** 默认由助理组织专家调查、给出推荐并沿用项目已有规范；普通、可逆的技术选择由团队在授权范围内决定并留记录。明显影响用户体验、费用、数据处理、长期维护成本或难以回退的取舍，翻译为用户能理解的选项并请用户决定。用户可要求查看全部技术细节或亲自拍板；本规则不绕过阶段确认及既定权限和预算。

**界面与交互设计确认：** 新增页面或明显改变操作流程时，设计负责人默认先提供关键界面、可点击原型或操作演示，由助理在会议共享区讲解，用户边看边反馈，确认后再进入正式实现。小修复和已有组件的常规调整不强制制作原型；具体采用何种设计产物按任务需要选择，不要求每个任务同时制作全部形式。

**已有项目接入：** 默认先做只读调查，检查已有 README、规范、架构、Issue、当前分支及未提交改动，形成简短的项目现状与待核实问题，优先复用已有计划，不直接重写文档或修改代码。大型仓库先了解结构，再围绕当前目标深入，用户可边讨论边调查，无需等待全仓读完。运行构建、安装依赖等操作另按授权执行；接入或只读调查不构成写入授权。

**项目推进方式：** D60 的两种方式均属于首发范围。里程碑方式围绕成果节点维护持续任务队列；Sprint 方式维护固定周期、本轮目标及相应计划、进展检视、评审与回顾节奏。助理协助设置与组织，不因选择 Sprint 而要求用户逐个调度 Worker，也不改变既定权限、预算及完成规则。具体交互及两种方式的切换仍需设计。

**Sprint 到期：** 按期结束本轮并保留实际完成情况，不自动延长或把未完成任务标为完成。助理总结未完成原因，提出下一轮安排，由用户确认；正在执行的工作可在原有授权和预算内继续，进入下一轮不自动增加预算。保留任务原属迭代与后续调整记录，不通过搬动任务抹去延期事实。

**会议与执行用量边界：** 会议讨论不消耗阶段执行时长，不设置会议费用上限。语音识别 ASR 与语音合成 TTS 使用独立的本地模型或 API，不计入项目用量；不将语音服务与项目执行混算。项目任务执行按 D25 以额度消耗为主要限制、时间为次要限制，并保留执行轮次上限；会议身份不免除由会议触发的后台任务执行限制。会议模型与执行模型的用量归属和展示细节仍需定义，不增加会议预算熔断规则。

**项目周期额度分配：** 用户设置每项目单位时间内允许消耗的总额度，默认按周，支持改为按月或按天；项目经理依据复杂度和执行需要灵活分配给任务，不机械均分或要求用户逐任务分配。并行 Worker、执行重试和独立验证均计入同一项目周期预算；达到额度边界不能通过新建阶段、切设备或换 Worker 重新获得一份额度。按量 API 使用金额口径，能读取订阅额度的服务按其单位控制，无法取得真实额度时提供明确标注的 Token 等估算控制；重置时点、额度不足、追加与不同服务单位换算待细化。项目周期额度与服务商真实余额分别记录，不因项目周期更新就认定服务商额度已刷新。

**多服务额度与耗尽处理：** 项目总预算由获准使用的各服务额度及其分配共同约束，分别记录，不把不同服务的百分比、Token 或货币余额直接相加。项目经理默认按职能和复杂度分配模型，用户可覆盖为统一服务优先级并设置切换阈值。全部已分配执行额度耗尽时暂停，询问用户是否分配新额度；用户不追加时，再询问是否允许新周期自动继续，而不是默认自动恢复。实际恢复仍需原任务授权有效、目标未变且对应服务确实可用；具体阈值单位、跨项目共享账号额度与周期对齐需验证。

**模型切换最低能力：** 支持用户设置任务最低能力要求；达到服务使用阈值后，只有满足该要求及既定权限、数据和预算约束的服务才可自动接力。不满足时暂停，由助理说明等待额度恢复、授权其他服务或缩小任务范围等选项，不静默降低已确认交付标准。最低能力的表达、判定及实际接续能力需验证，不能只靠模型名称认定通过。

**跨项目额度协调：** 多项目共用同一 AI 服务额度时，由长期助理统筹，用户可设置项目优先级；各项目经理在本项目获分配额度内调度。高优先级项目优先获得尚未分配的额度，不自动挪用其他项目已分配额度；需要调整时向用户提出简短提案并确认。服务账号的真实共享余额必须统一核算，不能由多个项目重复当作各自可用额度。

**空闲额度优化：** RSI 候选生成与评测为低优先级工作。默认没有 Agent 正在执行、项目仅等用户确认或验收时，允许在保留项目后续所需额度后使用充裕闲置额度；用户回复、项目恢复即停止派发新的优化调用并保存进度。支持更严格设置，例如全部任务都完成后才运行，或仅在额度周期即将重置且剩余充裕时运行；后者仍需满足正常工作优先和额度预留，不允许趁重置前抢占正常执行。按对应服务真实周期判断其额度是否将重置，不能只看项目预算周期。优化消耗单独记账并计入服务真实消耗，不挪用正常项目额度；已发出调用仍计入预留，取消能力及阈值需验证。启用候选需用户确认，不自行弱化权限、预算和验收标准。

**优化消耗评估与暂停：** 启动优化任务及后续每一轮前，评估候选生成、评测等所需消耗，并结合已用额度、在途调用、正常项目预留及剩余阈值判断是否可继续。预计继续会触及正常项目所需额度或预留阈值时，保存前序候选版本、修改记录、已完成评测、未完成项和用量，暂停后续优化；运行中用量变化也须重新检查，不能只在启动时判断。保存进度不等于通过评测或启用新版本，恢复时须重新核对额度和候选所依赖的版本。无法可靠评估的服务如何保守预留仍需技术验证。

**自动优化开关：** 首次安装后的启动引导询问是否开启自动优化，初始状态为关闭，未作选择也不视作开启。只有用户明确开启才允许触发候选生成与评测，且仍受闲置、消耗评估和正常项目额度预留规则限制；开启自动优化不等于同意自动启用新版本。

**优化版本生效：** 用户确认启用后，新任务使用新版本；已开始的任务保持原版本。已有任务只在明确的阶段边界，经检查后再切换，避免执行中途规则变化。执行记录须关联实际使用版本；未到切换边界不因更新全局设置而替换在途任务版本。具体检查项和回退机制仍需技术设计。

**纪要中的演进方向：** 先连通设备、由用户手动指定运行位置；再读取设备能力和状态，回答用户的选择问题；自动分发属于更后阶段，不是首发必需。设备建议首先核对操作系统、工具、权限、数据与任务要求，不能只做 CPU 排名。

**已确认的资源分流：** 小文档文本可以随通信直接进入群聊或 Agent 私信；大文件和代码经 GitHub 上传并由接收方拉取，不要求把每份小文本都先上传 GitHub。小文本的具体大小界限、来源和版本规则待 Q13 细化。

**纪要中的通信方向：** 类 Slack 群聊属于产品交互形态，局域网直连、中转服务器和 P2P 属于传输选择，技术路线仍待 Q16 决定。正文已确认仅可信设备解密、中转密文；具体密钥与恢复实现、密文和元数据的服务端留存仍待 Q15、Q16、Q22。三个用户可见汇报类别为启动、完成、异常；机器协议仍需确认、去重、取消、恢复等事件。

首发面向个人及其设备。多人组织、团队共享项目和管理员权限没有纳入已确认首发承诺。

## 推荐继续讨论的顺序

当前清单共 34 个议题组，包含大量已定原则的实施与验证工作，不代表仍需用户逐项回答 34 次。建议将剩余用户决策收敛为以下 6 组，技术细节先调查或通过原型提出具体方案，不再逐个询问：

- 首发交付边界与日期：软硬件分别发布和双向派工已定；剩余日期及公开版本边界（Q02、Q31）。
- 首个实际验收任务与体验者：具体 Issue、成功及失败样例、首批外测安排（Q01、Q29）。
- 关键默认策略：额度预留与阈值、提醒节奏、Sprint 周期等，先形成成套建议再确认（Q08、Q24、Q33、Q34）。
- 数据生命周期与恢复：记录保留、导出删除、设备丢失与恢复体验（Q15、Q22）。
- 首发视觉与角色表现：头像或形象、动效、自定义深度，已定每专家独立音色不重问（Q18、Q27）。
- 商业细则：30 天试用及不重置已定，剩余订阅价格、换绑执行和服务并发规则（Q30）。

以下原顺序保留为技术调查及实施规划顺序，不应据此继续重复采访已确认产品原则。

1. **Q01 与 Q02：首个项目和首发边界。** 先确定交付什么、给谁试、怎样算成功，再安排功能和期限。
2. **Q03、Q05、Q25 与 Q26：底座和 Windows 样机验证。** 技术团队先取得证据，避免把不支持的接口写成交互承诺。
3. **Q06、Q07 与 Q09：会议、确认和任务状态。** 形成一条可实现的交互主链。
4. **Q12 至 Q17：GitHub 与多设备协作。** 明确资源、身份、通信及助理接续的责任。
5. **Q08、Q10、Q11 与 Q23：预算、交付、集成和项目连续性。** 用同一个真实任务跑通。
6. 其余 P1 细节与外测并行细化；P2 保留为后续路线。

以上顺序是建议，不代表这些问题已获确认。验证项可先独立推进，产品问题继续一次讨论一个。
