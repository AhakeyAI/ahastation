## 2b. 远程控制与会议模式的其他竞品（10-23 补充，联网检索）

这两个方向上的产品不止上面三家。以下资料多为厂商页面和第三方比较文章，功能描述没有经过实测。

### 远程控制（手机 / 另一台设备控制编码 Agent）

| 产品 | 要点 | 对我们的意义 |
| --- | --- | --- |
| Anthropic 官方 Remote Control | 终端会话扫码与 Claude App 配对；只支持 Claude Code；据第三方文章，没有推送和语音，电脑合盖后会话结束 | 「手机看进度、追问」已是官方免费能力，**不能作为我们的卖点** |
| [Happy](https://github.com/slopus/happy)（开源） | Claude Code + Codex 的手机 / 网页客户端；需要批准或出错时推送；端到端加密 | 开源 E2E 远控的现成参考实现，B28 设计评审时对照它的加密与配对流程（使用前核对许可） |
| [Omnara](https://apps.apple.com/app/id6748426727) | 手机控制 Claude Code 与 Codex；据[比较文章](https://seawork.ai/en/blogs/omnara-vs-happy-vs-seawork/)，电脑离线时会话可以继续，支持双向语音与听写 | 「发起端离线继续执行」已有竞品宣称；我们的差异在于授权与预算在离线期间仍然受约束 |
| Grass、Cursor Mobile | 据[第三方文章](https://codeongrass.com/blog/is-there-a-mobile-app-for-claude-code/)，Grass 在一个界面里支持 Claude Code、Codex、OpenCode；Cursor Mobile 只面向 Cursor 用户 | 多 Agent 手机客户端是拥挤赛道 |

**结论**：「从手机控制 Agent」本身已经同质化（官方 + 至少 4 个第三方）。这印证了 10-03 策略「首发不做原生移动 App」。我们跨设备的价值应放在**两台电脑之间可信地派工与交接**（授权、预算、主持权、GitHub 版本、停止回执），而不是「手机遥控」。

### 会议模式（多个 Agent 以语音参会）

| 项目 | 要点 |
| --- | --- |
| [Agent Standup](https://www.it-connect.tech/agent-standup-turns-claude-code-and-codex-agents-into-a-video-call-dashboard/)（开源） | 把 Claude Code、Codex 等会话画成视频会议里的角色，用来观察并行子 Agent；上线三天 150+ star |
| [AgentCall](https://awesome.ecosyste.ms/projects/github.com%2Fpattern-ai-labs%2Fagentcall)（MIT） | 让编码 Agent 以语音 / 视频 / 共享屏幕加入 Google Meet、Zoom、Teams |
| [gstack meeting agents](https://www.producthunt.com/p/gstack-joins-your-meeting/ai-yc-interview-with-gstack-agents) | 基于 AgentCall 的角色（CEO、QA 负责人等）以语音机器人加入 Google Meet；推理在用户本机的编码 Agent 会话里 |

**结论**：多 Agent 语音会议还处在原型阶段，没有发现成熟产品，也没有中文多音色方案。这是我们差异化最明显的方向，但同时说明**用户习惯尚未建立**，B41 的非开发用户测试要重点观察大家是否真的愿意「开会」，而不只是打字。AgentCall 把 Agent 接入现有会议软件的思路可以作为后置功能（让 AhaStudio 的专家加入用户已有的 Teams / 飞书会议），首发不做。

## 4. 集成与复刻决策（建议）

原则沿用 10-21：公开接口依赖 > 薄 adapter > 边界清楚的源码移植 > 整产品 fork。

| 能力 | 决策 | 理由 | 落到 |
| --- | --- | --- | --- |
| 领域：项目、计划、决定、授权、预算、交付 | **自持，在现有代码上演进** | 差异所在；上游都没有 | B03、B08、B18、B19、B22、B23 |
| 本机 Harness 运行 | **保留现有 adapter 为主线**；Paseo 作为 B04 对照候选 | 现有 adapter 已有授权桥和 grant 绑定；Paseo 的停止接口未确认 | B04、B10 |
| 跨设备传输（发现、配对、中继、远端执行） | **B04 里加一组对照：Paseo connected hosts vs 自建中继**。倾向：远端执行面用 Paseo daemon（Apache-2.0，可分发），领域事件与授权回执走我们自己的协议 | 自建 E2E 中继是 XL（B28）；Paseo 已有配对确认、relay、密码检查。但它是 beta，且我们的主持权和回执语义它没有 | B04、B27–B31，见 `../design/remote-control.md` |
| 订阅窗口观测 | **两条路并存**：自有 adapter 读 Claude/Codex 协议（B06 WIRING）；若 B04 选 Paseo，则改读 `listUsage` | 观测来源可替换，账本不变 | B06、B19 |
| 中文 ASR / 多音色 TTS | **自建，基于 sherpa-onnx**（Apache-2.0）+ 在线 API 兜底 | 上游全空白；B05 实测决定模型 | B05、B11、B13 |
| 会议编排（Host、专家、发言队列） | **自持** | 上游全空白 | B12、B13，见 `../design/meeting-mode.md` |
| 看板组织（Issue / Squad / 职能） | **参考 Multica 的概念，不复制代码** | 许可限制 UI 派生与嵌入 | B15 |
| Worktree、Diff、终端 | **参考 Orca（MIT），必要时按文件移植并保留 NOTICE** | 不依赖其内部模块的稳定性 | B21 |
| 移动端 | **首发不做原生 App**；用可信网页 / IM 深链处理 Decision（10-03 策略不变） | Orca、Paseo 都有手机端，正面竞争成本高 | B32 |

## 5a. B04 实测结论（2026-10-23）

已在 N5095 上实测 Paseo 0.12.0（见 `../b04-runtime/README.md`「完整矩阵」）：**不采用 Paseo 作为执行层或跨设备传输**（ADR 0004）。主因是 Codex 在 Paseo 下没有逐操作批准的模式，工作区内写入不经宿主，一票否决项 S4 失败。上文第 4 节表中「本机 Harness 运行」「跨设备传输」两行据此改为「保留现有 adapter」「自建」；Paseo 降为设计参考（后台独立运行、断线保留待批准请求、用量窗口数据结构）。

## 5. 需要用户拍板的一项（已由 B04 证据回答，见 5a）

**是否接受「远端执行面可以基于 Paseo daemon」这一方向**（即 B04 把 Paseo connected hosts 纳入对照，如胜出则跨设备 X 节点改为「我们的领域协议 + Paseo 传输」，B28 规模从 XL 降为 L）。代价是引入一个快速迭代的外部依赖，需要固定版本并承担升级；收益是跨设备节点可能提前。不接受则按原计划自建中继。
