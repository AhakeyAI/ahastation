## 实现取舍

- 继续使用 `WorkerScheduler`、`TaskMailbox`、`MeetingRepository`、`TaskWorkspaceManager` 和现有交付流程。新增入口接入这些模块，不再建立一套任务状态或消息存储。
- 保留现有四个 terminal adapter。先接通公共任务能力，遇到真实 CLI 差异再修改对应 profile。
- CLI 桥用 Node 自带 HTTP，绑定 `127.0.0.1`，由 main 承载。一个小服务、一个命令入口即可；不引入服务框架、数据库、消息队列或通用插件系统。
- 必要校验放在外部请求入口：任务凭证、当前 attempt、参数格式。内部用类型和明确错误传播，不层层重复校验、不为未知异常自动换后端或重发任务。
- UI 优先沿用任务面板、终端和确认入口，只补实际执行后端、阻塞原因和报告状态。

## 第一交付：两种 CLI 跑通完整任务

这是优先实施的范围，使用现有 Coordinator。

### 工作内容

1. **确认现有路由可用。** 安装依赖并跑一次基础检查；核对计划中的 executorBackendId、实际启动命令和工作目录。根据本机可用认证，选两种现有 terminal CLI 做首批验证；未安装的 CLI 不阻塞其他两家。
2. **新增薄 CLI 桥。** 提供 `aha-worker report --file <json>`、`ask --file <json>`、`inbox` 三个入口。入口随应用分发，启动 Worker 时提供命令路径和当前任务凭证；Windows 路径含空格/中文时可用。复用已有提问、邮箱及报告逻辑。
3. **报告有明确回执。** 报告落入现有 journal 后再回复“已接收”，后续验证与审查异步运行。相同报告重复提交返回原结果，旧 attempt 的报告不改变当前任务。沿用现有消息 ID 和状态，不另建操作账本。
4. **代码结果进入现有交付流程。** Worker 报告包含文件、测试和未解决项。提交时对照其 worktree 实际变更；有改动却报空 files 时提示修正。人工完成入口也使用实际变更清单，测试未提供则如实记录，不伪造通过。
5. **补足基本启动处理。** 复用当前 readyPattern 和登录识别；已识别登录/信任阻塞时保留待发任务，显示原因，由用户处理后继续。无就绪证据时不把定时器到期当作已经执行，也不自动重复粘贴。具体匹配只针对首批 CLI 的实际输出。

### 主要落点

- 新增 `electron/worker-cli-bridge.ts`：本机请求入口与现有任务方法的连接。
- 新增 `electron/worker-cli.ts`：CLI 参数、请求和结果输出；构建时生成随应用携带的启动入口。
- 修改 `electron/backends/terminal-cli-adapter.ts`、`electron/worker-scheduler.ts`：任务说明、上下文传递与启动处理。
- 修改 `electron/orchestrator.ts`、`electron/meeting-repository.ts`：可等待的报告接收和恢复处理；邮箱优先直接复用 `electron/task-mailbox.ts`。
- 修改 `electron/ipc/worker-pty.ts` 及必要的交付代码：人工完成报告与真实变更一致。
- 只在实际需要时调整 `src/components/TerminalTurnConfirmBar.tsx` 和任务面板。

文件名是实施落点，不要求把每项拆成新模块；如果已有函数能承载，直接扩展。

### 验收

一个计划派给两种不同 CLI，在独立 worktree 修改各自文件。其中一个提问并收到主持人答复；两者通过命令提交完整报告，现有流程产生可审查的代码结果，用户验收后任务才完成。无需用户复制终端输出来充当交付报告。

完成这条流程即交付第一版，不顺带扩展 Agent 数量、引入 daemon 或重做状态系统。

## 第二交付：四家可用，CLI 能指挥 CLI

依赖第一交付完成。

1. 将相同流程覆盖到现有 Claude、Codex、Kimi、Qoder terminal backend；修复已观察到的命令参数、输入和报告差异。
2. 合并前后端重复的 terminal ID/显示信息，使用一个小的共享定义。CLI 专属启动逻辑仍放各自 adapter，不设计万能配置语言。
3. 为协调者角色增加 `aha-meeting` 命令入口，直接映射现有 `executeMeetingCommand` 支持的计划、派发、查询和答复操作。沿用现有计划审批及角色边界，Worker 凭证不能调用主持人操作。
4. 先让一种真实终端 CLI 担任主持人，派发给另一种 CLI。验证后再开放该后端的 coordinate 能力，其他后端按同一流程逐个接入。
5. 新增 Agent 按实际使用需要逐个做；OpenCode terminal 可作为首个扩展，不以追齐 Orca 的目录数量作为本阶段目标。

验收：现有四家都能接单和报告；至少一次四个 Worker 并发，以及一次“CLI 主持人 → 不同 CLI Worker → 结果回传”的完整流程。UI 显示实际执行者。

## 第三交付：应用重启后接回原终端

依赖前两次交付的任务闭环。先做小型 Windows 进程存活试验，证明可行后再接业务。

1. 把现有 PtyHost 移到独立 supervisor，main 经一个异步 client 调用。沿用现有输出缓存和界面。
2. 保存 terminal、meeting、task、attempt 和工作目录的绑定，区分“断开界面”与“结束任务”。重连保留 hook 文件，不重新启动 CLI、不重发初始提示词。
3. main 重启后重新发布 CLI 桥地址，存活 Worker 的命令能找到它。桥离线时命令明确返回未确认接收；恢复后可重试同一报告，由第一阶段的去重处理兜底，不增加后台消息服务。
4. 增加“保留任务并退出”与“结束任务并退出”的明确操作。后台只保持已经运行的终端，任务编排和审查仍由 main 承载。

验收：Windows 打包版主进程退出或被强杀后，原 CLI 仍存活；重新打开应用可以操作同一终端、继续原任务；重复报告不重复交付；明确停止后自有进程退出。

系统重启恢复、supervisor 自身崩溃后的自动复活、跨版本热迁移、多控制端和远程主机不属于本次交付。后台工作需要这些能力时，再按真实问题增加。

## 验证预算

测试跟随上述交付，不为每个函数新增测试。

- **第一交付：** 一组离线集成测试覆盖两 Worker 路由、问答和报告交付；补重复报告、旧 attempt、启动阻塞三个关键回归场景。现有文件差异和交付测试直接复用，只为新缺口加断言。
- **第二交付：** 复用第一组场景验证新增 profile；补角色权限及终端主持人的主流程。每家做一次有记录的真实 CLI 冒烟，不做四家两两组合的完整矩阵。
- **第三交付：** 验证保留退出、main 强杀重连、明确停止三种生命周期，再覆盖一次断连期间报告重试。先跑 Windows；对声明支持的平台在发布前各补一次针对性检查。
- 每次代码交付执行 `npm run typecheck`（覆盖 renderer 和 Electron）及相关测试；阶段收尾执行一次 `npm test`。没有新变更或失败，不反复跑全量。
- 真实 CLI 主流程需记录使用的版本和结果，模型调用在已授权的费用范围内执行。离线通过与真实 CLI 通过分别报告。

## 实施纪律

每次完成一个可用交付，再决定下一次具体改动。只修复影响当前流程的问题，不顺带重构整个 orchestrator，不追求通用框架，不把未知状态改成成功。

用户原有修改和 Orca 参考仓库保持原样。实现授权不包含提交、推送或发布；这份规划本身也不启动实施。
