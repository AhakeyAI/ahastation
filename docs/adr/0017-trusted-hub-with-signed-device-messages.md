# 0017 首版跨设备：受信 Hub + 设备签名

- 状态：已接受（2026-10-26，用户裁决冲突表 C01）。**2026-10-27 待复核**：本决定会让首版暂不满足 AME-D47（中转只见密文），裁决时冲突表没有写明这一点
- 日期：2026-10-27
- 关联：R2 `docs/c0/review-etrnal-dev/CONFLICTS.md` C01、C02、C08、C10；`etrnal-dev` 的 Hub（`services/remote/hub`）；部分延期 ADR 0014

## 背景

`etrnal-dev` 的 Hub 跑在微信云托管 + MySQL 5.7 上，在服务端用明文做会议快照、去重和计划投影。ADR 0014 要求中转只见密文；如果照办，这些服务端逻辑都要搬到客户端，约等于重做大半个 Hub。

评审时找到的主要风险不是「Hub 能读到内容」，而是「Hub 能伪造任务」：执行端的本机授权只限制目录和 Agent，不判断任务是不是用户发的。被攻破的 Hub 可以在用户已授权的目录里让 Agent 执行任意指令。

## 决定

1. 首版 Hub 是受信中转，可以读取会议内容。设置页和隐私说明里写明「协作服务能看到会议内容」。
2. 设备发出的每条消息都要带设备签名：会议消息、计划提案与批准、任务派发、补充、继续、停止、工具审批，以及设备撤销。Hub 只转发和存储，自己不产生需要设备执行的内容。
   - 签名用 Ed25519，实现与 ADR 0014 相同：libsodium，规范 CBOR 作为签名输入。
   - 签名覆盖 `msgId`、类型、会议 / 任务 / attempt、`basedOn` 版本、`issuedAt`、`expiresAt`、发送设备、`keyId` 和正文的 hash。
3. 接收方（执行设备、协调设备）在应用消息前依次校验：签名有效；发送设备在本机保存的可信设备列表里；没有过期；`msgId` 没有见过；`basedOn` 不是旧版本。任何一项不通过就拒绝，并在界面显示原因，不静默丢弃。
4. 设备公钥**不能只靠 Hub 下发**。新设备的公钥要由一台已有可信设备确认后，才写入各设备本机的可信列表；第一台设备除外。这一条依赖 C08 选 b。
5. 私钥存 Electron `safeStorage`，使用异步 API（PR #53 已迁移）。
6. 内容加密（ADR 0014 的 X25519 封装、`secretstream`、项目密钥轮换）延后到下一版，届时写新 ADR 替代本条的第 1 项。

## 后果

- 好：
  - Hub 被攻破或运营方越权时，只能读、丢弃、延迟消息，不能让任何设备执行它自己编的内容；
  - 重放会被 `msgId` 去重和过期时间拦住；
  - 签名链和 ADR 0014 的 L1 是同一套，以后补加密时不用推翻。
- 坏：
  - 会议内容在云端是明文，D12「30 天密文信箱」的前提不再成立，保存期限按 C02 另定；
  - 撤销设备只能阻止它以后签名和接收新内容，已同步到那台设备的内容收不回（D11 的提示照旧）。
- 风险：如果 C08 最终选 a（登录即注册、无需已有设备确认），第 4 项不成立，Hub 可以替攻击者注册一台设备再用它签名，签名就只能防传输中篡改。

## 考虑过的其他方案

- 完整端到端加密（ADR 0014 原样）：安全性最好，但首版成本约 XL，并且要重做 Hub 的服务端逻辑。
- 只签执行类命令、不签会议消息：开启「自动批准计划」（C15）时，伪造的会议消息可以经 Host 生成计划并被自动批准，绕过签名。改为全部签名，成本几乎不变。
- 保持 Hub 现状、不签名：Hub 被攻破等于用户所有已授权目录被远程执行，否决。
