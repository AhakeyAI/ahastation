# 0019 Worker 跑原生 CLI，审批经全局 hooks 转给宿主

- 状态：已接受（2026-10-28，用户逐项确认）
- 日期：2026-10-28
- 替代：ADR 0016 的执行部分（Worker 不再走 SDK adapter）；ADR 0018 第 1、2 条（跨设备执行端不再复用 TS adapter）
- 关联：AME-D32、D33、Q20（本条改变了它们）；G4、G8、G13；C04、C14、C16；B04；PR #49（Leo，`origin/pr49` @ `77e07ae`）；变更说明 `../c0/design/native-cli-worker.md`

## 背景

ADR 0016 选定「SDK + 现有 adapter」作为唯一运行底座，A-14–A-20 和 B04 的严格停止、宿主裁决写入都是在这条路径上证明的。这条路径的问题是用户看不到原生界面，也无法插手；而用户要的是：

- 每个 Agent 有自己的会话，点开就是原生 CLI；
- 必要时可以接管；
- 本机已有的 Agent 会话（包括用户在系统终端里开的）都能被发现、归类，并收编进 AhaStudio。

Leo 的终端工作区（PR #49）已经有终端守护进程、标签式本地 CLI 工作区和 Worker 回报通道（`aha-worker report / ask / inbox`）。2026-10-28 核对过，Claude Code 和 Codex 0.156.1 都有能返回 allow / deny 的 PreToolUse、PermissionRequest hooks（Codex 需要打开 `codex_hooks` 特性开关）。Orca v1.4.218 已经用全局 hooks 管理 19 家 CLI 的状态。

## 决定

1. **运行方式按角色区分**
   - 执行 Worker 和独立复核：默认跑原生 CLI，每个 Agent 一个终端会话。子 Agent 由 CLI 自己编排，不单独开终端。
   - Host（长期助理）和会议专家：默认走 SDK。点开时显示由 SDK 事件生成的只读视图；接管时先暂停，再用原生 CLI 续接同一会话（Claude 用 `--resume`；Codex 的做法在 B04 重跑时实测）。
2. **审批**：Worker 的权限请求经 PreToolUse / PermissionRequest hooks 转给宿主，按项目授权裁决，和 A-17 是同一套机制。授权仍在模型之外强制执行。
3. **Worker 准入**：一个 CLI 要当 Worker，必须同时满足三条：能在工具调用前拒绝；有轮次结束信号（Stop）；通过 B04 关键场景实测。首批只有 Claude 和 Codex，其余 CLI 只能作为手动终端使用。
4. **结构化事件来源**：
   - 轮次结束：Stop hook；
   - 工具事件：PostToolUse hook；
   - 用量：读会话日志；
   - 成果：`aha-worker report`，回报通道要带凭据，只对当前 attempt 有效。
5. **严格停止**：发出停止后，宿主对该会话的 PreToolUse 一律拒绝，再中断当前轮次；超时则结束进程树。停止前已批准、尚未执行的命令一并撤销，语义与 A-20 相同。
6. **接管**：
   - 随时可以接管；
   - 接管期间宿主不再向该会话发指令；超出授权的请求弹给用户确认，不自动拒绝；用户的操作在证据里标为人工；
   - 交还后，Agent 先读工作区差异和用户的改动，再继续；
   - 交付仍要经过独立复核。
7. **全局 hooks**：
   - 和 Orca 一样写进用户的全局配置（`~/.claude`、`~/.codex` 等），用标记块圈出我们写的部分，卸载时清理干净；
   - 用户自己开的会话只上报状态、立即放行，审批照旧由 CLI 自己问用户；
   - AhaStudio 没有运行时，hook 立即退出，不拖慢 CLI；
   - AhaStudio 派出的 Worker 会话连不上宿主时，一律拒绝（宁可停住，也不放行）；
   - Station 等内部组件启动的会话要登记归属（见变更说明 §9.3），避免被当成用户自己的会话。
8. **会话扫描与收编**：
   - 程序启动并经用户授权后，扫描本机所有 Agent 会话和 AhaStudio 历史任务，按文件夹、项目、工作树、分支归类，项目身份按 ADR 0013；
   - 发现一个新的独立项目时推系统通知，引导用户到 Studio 弹窗里确认授权；
   - 收编时先备份会话文件，再复制出一个新会话，在 Studio 的原生终端里续接，然后提示用户结束原来的会话；
   - 收编后的权限不超过本机项目授权（C04）。
9. **跨设备**：
   - 执行设备上启动和管理 CLI Worker 的是终端线（Leo 的守护进程和执行端）；
   - Station 只负责编排：派发、回执、核对、状态同步；
   - 设备连上 Hub 后，协调端能看到这台设备的会话清单：只发元数据，用户自己的会话只列出授权共享的项目；
   - 远端会话可以经 Hub 实时只读查看（只限 Worker 终端），接管必须在执行设备上进行；
   - 内部阶段 Hub 上的终端内容是明文，所有设备消息要签名（ADR 0017）。
10. **门槛**：Worker CLI 桥合入前，在 CLI 路径上用 Claude 和 Codex 跑 B04 的 S1–S6、S8、S11。S4–S6 一票否决，有一项不过就不合入，Worker 继续走 SDK。

## 后果

- 好：
  - 用户能看见每个 Agent 在做什么，也能插手；
  - 各家 CLI 的原生功能（斜杠命令、插件、模型切换、登录）原样可用，与 G13 一致；
  - 本机已有会话可以纳入项目管理。
- 坏：
  - B04 的结论要在 CLI 路径上重新证明；
  - 结构化数据要从 hooks 和会话日志拼出来，界面一改就可能失效，需要每周兼容检查；
  - 全局 hooks 会动用户的配置文件，安装、升级、卸载都要可回退；
  - 每个 Worker 多一个 PTY，N5095 默认并发仍是 2（G6）；
  - 跨设备执行端要从 Python 驱动 Codex 改为调用终端线的执行端，`etrnal-dev` 的 `station_codex.py` 执行部分要退役。

## 考虑过的其他方案

- **只走 SDK，点开时只读**：能保留 B04 结论，但看不到原生界面、无法直接插手。Host 和专家采用了这个折中，Worker 没有采用。
- **会话级 hooks**（Leo 当前的做法，用 `--settings` 或独立配置目录）：不动用户配置，但扫描不到用户自己开的会话，否决。
- **独立配置目录**：最干净，但会丢掉用户已有的登录和设置，否决。
- **对没有 hooks 的 CLI 解析屏幕上的审批提示**：太脆弱，只作为显示用，不作为授权依据。
