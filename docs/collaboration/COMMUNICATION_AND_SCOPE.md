## 2. 通信拓扑建议

继续使用现有微信云托管上的 Hub 作为公网中转和共享状态服务。两台 Station 都主动向同一 Hub 建连，不依赖同一局域网，不要求用户为电脑准备公网 IP 或配置端口映射。

~~~mermaid
flowchart LR
    A["Station A：界面、Host、本机执行"] <-->|"HTTPS 控制／快照；WSS 实时事件"| H["微信云托管 Hub"]
    B["Station B：界面、本机执行"] <-->|"HTTPS 控制／快照；WSS 实时事件"| H
    H --> D["MySQL：共享状态、幂等记录、待投递项、事件"]
    A <-->|"Git 获取／推送"| G["用户指定的 GitHub 仓库"]
    B <-->|"Git 获取／推送"| G
    A --> LA["A 本机 Agent／原生对话"]
    B --> LB["B 本机 Agent／原生对话"]
~~~

首版不新增 P2P、内网穿透、个人 VPN 或附件中转系统。Hub 是轻量协作服务，Host 和实际 Agent 仍在电脑上执行。

Windows、Linux、macOS 使用同一业务协议。不能按操作系统继续拆成一端长连接、另一端固定轮询 Prompt 的两套流程。

## 3. HTTPS 和 WSS 的职责

| 通道 | 用途 |
| --- | --- |
| HTTPS | 登录／恢复、注册设备、配置设备／项目、提交聊天／任务控制／审批决定、查询快照、补拉持久事件和核对执行状态 |
| WSS | 订阅账号及会议变化，接收待处理任务通知、停止通知、审批、进度／输出事件和在线变化，执行端回传确认及状态 |
| 本机 IPC／内部组件 | 界面与可信主进程通信；读取本机授权、调用 Agent／Codex 共享服务；不向公网暴露本机执行接口 |
| Git／GitHub | 选定输入与成果文件的实际内容、准确版本、独立任务分支和 PR |

建议控制请求优先通过 HTTPS 提交，事务提交后通过 WSS 通知相关设备；执行端 ACK／状态可经 WSS 进入同一持久化处理器。不同通道只是传输入口，不维护两套任务状态，也不因 WSS 发送成功而认定业务执行成功。

正常联网时，两端通过推送及时刷新，无需客户端每隔一两秒拉取所有 Prompt。重连时的补拉和核对属于恢复流程；心跳只判断连接状态，不证明任务已启动、停止或完成。

消息正文、选定原生对话内容和执行事件会经过 Hub；附件与成果文件本体仍按已确认规则走用户指定的 GitHub 仓库。Hub 不是端到端加密中继，不能声称云端完全看不到消息正文。

## 4. 一次任务如何走完整链路

1. A、B 同账号登录，各自注册并建立带身份的连接；Hub 校验账号归属，向两端提供同一设备目录和会议状态。
2. 用户发言通过 HTTPS 保存到共享会议，Hub 将对应事件推送给双方；只有该会议的唯一 Host 进行统筹。
3. Host 在批准计划与分配规则下产生完整业务任务，持久保存任务、目标、输入版本和稳定请求身份。
4. Hub 将待处理通知发送给 B。B 根据本机真实配置核验项目、目录、Agent 和权限，并把任务保存到本机后确认接收。
5. 收到 B 的持久接收确认后，Hub 才记录“已接收”。收到 HTTP 请求、写入待投递项或把消息发进 socket 都不能代替这一边界。
6. B 获得本机执行名额并启动 Agent，回传进度、必要审批和结果。Hub 保存状态并推送给两端。
7. B 按任务要求推送成果提交和 PR，Hub 仅同步引用；A 可在 PR 合并前取得准确成果。

已有 Codex 对话走同一认证、通信和恢复基础，但执行目标是精确原生对话及轮次，不重新拆成新任务，也不启动独立写入者抢占原桌面服务。

停止和审批也通过这条链路处理：停止精确作用于目标轮次，真实退出后才能释放资源；同一审批只接受一次有效答复。A 离线时，不因 B 仍连着 Hub 就放开已约定禁止的新分配、补充执行和继续操作。

## 5. 持久化、重连与防重复

长连接负责及时通知，MySQL 和本机任务日志负责可恢复。建议实现下列基础：

- Hub 将业务状态与对应持久事件／待投递项在同一事务提交，避免“已收请求但无可恢复通知”。
- 控制请求带稳定请求 ID；超时重试复用原 ID。业务任务、执行尝试、原生轮次和网络请求保持不同身份。
- 使用现有账号范围递增 seq 和实体 revision 的契约，生产端持久实现快照、补拉和订阅；客户端按游标及版本去重，不能按消息时间戳决定新旧。
- 建立心跳、连接代次和退避重连；新连接替换后，旧连接的迟到断开不得把设备标成离线。
- 快照包含一致的事件边界，随后衔接增量事件；游标已超过保留期时明确重取快照，不能悄悄丢失中间变化。
- 重连先核对原任务的接收、执行、结果和真实退出证据，不自动再起一次 Agent。未知保持待核对。
- 关键业务记录、接收回执、停止证据和结果引用按业务生命周期保存，不以临时 socket 或会清理正文的旧 journal 作为唯一记录。
- 输出增量可批量发送并设置队列／大小上限；持久任务状态、最终结果、审批与停止事件不能因为输出过多而被丢弃。

网络允许重复传送；接收端通过持久回执、稳定身份及执行前核对抑制重复副作用。不能宣称换成 WebSocket 就自动获得“只执行一次”。

## 6. 本机权限与共享项目如何接入

共享项目描述“用户指定的哪个仓库或资源”，本机绑定描述“这台电脑允许在哪个实际目录执行”。A 与 B 可以绑定同一仓库的不同路径。

Hub 保存逻辑项目身份、设备就绪与绑定摘要；不接收可直接获得本机执行权限的远程 cwd。每次真正执行前，可信本机运行时从自己的持久配置解析目录并重新核验，Agent 真实权限不得超过本机授权。

现有四项契约需要真实生产实现，具体包括：

- DeviceDirectory：真实注册／配置／目录，接入认证、数据库、凭证和连接状态，而不只调用 mock。
- ProjectDirectory：真实项目元数据与路径无关绑定摘要，配合本机绑定配置的持久保存。
- LocalProjectAccessPort：注入生产项目／授权／Agent 状态，在执行前真实调用；撤权先保存并停止受影响执行，旧摘要不得覆盖。
- CollaborationChanges：生产快照、补拉和实时订阅；设备／项目的变化继续约束会议与调度。

当前资源模型只覆盖 GitHub 仓库和有限权限。纯文字／普通任务目录及明确授权完全访问会话，需要版本化扩展和两侧校验，不能删掉校验或只修改界面选项。

## 8. 微信云托管与数据库改造

继续复用现有 Hub 的部署基础，不要求用户购买另一台自管服务器。云端仍需部署新版服务及显式数据库迁移，已有健康检查返回 ok 不能证明新路由已经具备。

首版建议沿用现有单实例、单 worker、单版本接收全部流量的边界。当前 Hub 的 socket 连接表在进程内，MySQL 不会替其他实例转发 socket；A、B 落到不同实例会出现目录／投递／停止不一致。首次运行不为扩容引入 Redis 或额外集群，但必须明确限制，发布重启后靠持久状态和客户端重连恢复；将来扩容要增加连接归属及实例间分发，不能只调大副本数。

实施时必须完成：

1. 核验实际 HTTPS／WSS 服务入口、证书、升级握手、鉴权 Header、连接超时、心跳及发布重连；不直接把旧截图的网址当成已验证正式域名。
2. 将经验证的服务入口写入打包配置；当前 resources/remote-service.json 的 serviceUrl 为空。hub.ahastation.com 仍需确认实际域名绑定和访问，不因创建服务而自动生效。
3. 新增版本化的设备、项目／绑定摘要、会议、成员、聊天、任务／尝试、审批、事件／待投递及幂等记录，复用或迁移现有数据，不清空已有业务库。
4. 更新 Hub 源码导出白名单、容器 COPY 内容、依赖、迁移脚本和健康／就绪检查；现有导出器不会自动包含所有新增契约资源。
5. MySQL 内网凭证和 HUB_SECRET 只在 Hub 配置，Station 仅保存自己的协作凭证，本机模型／GitHub 凭证仍留本机。
6. 在测试环境验证新协议与现有远控共存，再进行实际双机安装包验收；不因本文整理直接改动云端资源。

## 11. 原会议、Host 与协作接口的整合（2026-10-22）

用户确认的目标是同一个会议窗口完成邀请电脑、提出目标、Host 拆分、计划批准、分配、进度和成果查看。当前独立 SharedMeetings 面板不能作为最终交付；不是新增另一种与原会议并列的产品模式。

### 11.1 当前可复用能力与缺口

- electron/preload.cjs 暴露 collaboration.request 和 collaboration.onChanged；src/types.ts 已声明。原会议、参与者和 TasksView 都可以调用，不需要通过打开共享面板才能取得数据。
- StationService 的 status／view 返回设备、项目、会议、消息、任务、审批等快照与本机状态；command 允许受限操作，本机交付、目录授权等另有专用 action。继续由主进程执行鉴权、命令校验、持久待投递和网络请求，界面不直连数据库或绕过本机授权。
- 原 TasksView 使用 meetingStore 聚合的 CrossProjectTasks；候选共享实体未接进该投影。不能直接把不同任务状态和执行设备语义压成现有本机字段。
- 共享 SharedCoordinator 使用独立模型线程与 station-plan；原 Orchestrator 使用原 Host 的 plan_meeting／proposePlan、批准和 scheduler 流程。统一界面时需收敛为同一会议的一套 Host 计划与派发权威，不能仅把两个组件同时摆进一个窗口。

### 11.2 建议实施顺序

1. 建立原会议视图身份与共享会议身份的持久关联，明确本机视图、Hub 业务实体和原生对话不是同一类身份；恢复和切换会议先核对关联，不重复创建会议或 Host。
2. 建立供原主界面消费的协作投影和命令适配：同一份共享快照经订阅更新参与者、聊天、计划、任务、审批和成果；任务以稳定来源和原 ID 定位，保留设备、Agent、原生对话和尝试身份。原本机功能继续工作。
3. 将原会议 Host 的统筹与计划批准链路扩展到跨设备执行目标；设备目录、能力、授权和名额作为 Host 上下文。该会议每条普通输入只投给一位 Host，已有原生对话点名仍明确直达，不同时触发另一份拆分。
4. 由统一派发入口把计划目标路由至本机或远端执行适配器。共享任务的接收、执行和结果经同一权威链同步；原调度器不得因看见一张远端卡片又在本机启动一次。协调设备在线与权限限制继续生效，远端界面操作须转换为受支持的请求，不能用放宽 Hub 协调权限解决。
5. 保留原 PlanMeetingModal 的可读计划、UserTasksPanel 的任务表、TasksView 的看板、TaskInspector／DeliveryViewer 的详情。扩展“设备＋Agent／原生对话”、真实阶段与远端成果来源；取回准确文件后提供预览、验证、提交与 PR。原始 JSON 留作诊断，不要求把全部内容重做成新卡片。正常流程替换独立共享入口，迁移期间的临时调试入口不计作产品完成。
6. 补主界面消费真实协作状态的集成与回归验证，再进行安装包双机验收；覆盖同一目标一次拆分、批准一次派发、两端同任务同结果、界面切换不重跑及原本机会议不回归。

### 11.3 已确认的本机与调度约束（Q75、Q78；Q74 已被更正）

- 本机在执行设备列表中由用户勾选，明确标注“本机”，不自动选入。当前共享面板创建时已有这项基础能力，主界面整合保留即可，无需增加默认开启的专用机制。未选入不影响主持与查看，移出不自动停止已有任务；全设备接收开关、Agent／项目授权和并发限制继续生效，勾选不能覆盖它们。
- 自动分配依据 Host 已展示的设备＋Agent 安排执行；移除当前 doPump 中按 activeTasks 升序取首项并覆盖目标的行为。负载可作为 Host 提案上下文，但不能在派发时静默换目标。
- 目标暂不可用时保留目标并显示具体等待原因；需要改变安排时由 Host 提出明确修订，展示原因与新目标，沿用手动／自动批准规则。未被执行端接收的任务和已接任务须区分，后者保持原设备核对，不开发迁移。

上述步骤是技术方案，不代表已经完成代码改造；不因文档中的建议扩大首版到协调设备移交或已接任务迁移。

### 11.4 计划与交付语义的复用核验

统一前先建立原计划正文／任务字段与共享计划字段的显式对应，再将其接到单一统筹入口；同一业务任务各视图保持关联，传输尝试身份和原生对话身份仍分别保留，不靠强改 ID 混成一种对象。保留原可读目标、取舍、步骤、风险、未决问题及验收要求，不能缩减为仅能派发的 JSON 数组。

原 WorkerScheduler 的结构化 WorkReport、DeliveryHarness／审查与共享 StationService 的 Git 交付目前是不同路径。需要明确远端交付如何提供完整报告、可获取成果、实际测试和待解决项，并映射到原成果查看与 Host 检查流程；不能把运行摘要或 tests 字符串当作原交付审查已完成。现有 GitHub 成果获取、独立工作区、权限和恢复机制继续保留。

原界面复用核验还包括正文编辑是否真正提交、设备真实容量替代固定 4、远端目录不能作为本机可读路径、原最终工作区发布不能直接当作 PR 合并动作。以上属于整合正确性检查，不是本轮已完成代码。

### 11.5 Q80–Q82：协作接入与原功能保护

正常接入压缩为 Station 账号与本机、按需 GitHub、按需仓库与目录三个区域，已有身份检测与设备注册／连接在客户端组合调用。纯文字无需仓库。恢复、撤销、LAN、自托管、旧 Bridge 和组合验证命令留在高级区域，目录授权及三类登录分别保留，不以缩短表单为理由绕过执行边界。现有 GitHub 仓库读取校验可复用，完整登录引导仍需补充。

聊天沿用 SideDrawer 的群聊和 @ 候选，扩展设备和原生目标标签及稳定路由，保留附件、技能、语音和快捷键；不新增收件人下拉框。同一消息在直接原生接续与 Host 统筹之间只进入正确路径。其余原单机及不冲突功能禁止顺带改造，新增协作故障应隔离；当前候选的窗口关闭条件范围仍须收窄，详见 [源码与回归审查](UNRELATED_FUNCTIONS_AUDIT.md)。正式验收增加 T34–T36，原型演示不能代替这些产品测试。

Q84 已确认采用过渡退役：正常界面按设备与 Agent 展示，旧 Pocket Vibe adapter 在内部保留旧记录／连接／执行核对能力；新链路替代及迁移验收完成后再移除。新版 StationService 不调用旧 PocketVibeSession，但原会议恢复和旧投递取消仍依赖旧适配器，迁移前不得切断这些入口。Hub、数据库、账号和原生共享组件不是该旧 adapter 的同义词，不随品牌一起删除。

### 11.6 Q86–Q92：接入、会议项目与远程接续的边界

Agent 自动检测和已有本机登录复用，首次本机共享授权后正常直接使用，异常才进入原设置。邀请列表按设备＋Agent，已参会对象临时断线保留身份。普通 Agent 有会议专属交流上下文，尚无正式任务也能被 @；任务执行上下文仍单独隔离。

Q91 已确认新建保留项目／目录和 Host 选择，原首页、默认 Host、最近项目及会议恢复保留；纯文字免用户目录，项目缺项可就地补齐。Q92 已确认加入既有会议不新建 Host、不强制先绑定项目，文件访问／执行前再由对应设备绑定本机目录。读取源码同样属于文件访问，不能用“讨论”名义绕过；共享项目身份和每设备绑定／任务工作区分别管理。

Q90 已确认原生对话作为远程接续关联对象：会议主聊天自动展示本次指令、状态及结果摘要，选定原历史在详情中查看；其他 Agent 输入仅包含明确引用／任务所需摘要，不自动包含整条原生历史。投影、订阅与模型上下文组装必须同时遵守，不能只改显示。验收补 T37–T39，当前只更新方案、未改生产链路。

### 11.7 Q93–Q95：普通参会与项目切换

普通参会 Agent 的会议背景摘要独立于原生远控链路；按需了解目标、已确认计划、关键决定与相关成果，不在每次加入时自动读取全部历史或调用模型。原生对话仍保留独立已有上下文及 Q90 分享范围，不能合并叙述为同一机制。

会议已开始文件任务后保持原主项目及任务工作区；切换另一项目时继续或新建其会议，不修改旧任务目录。普通群聊默认 Host 回应、@ 由明确对象回应，Host 可咨询专家；不广播调用全体模型，进度、成果、审批主动回报保留。新验收 T40–T41 待实施与运行。

### 11.8 Q96–Q97：原编排能力与成员／任务关系

正常流程不再额外要求开启“多 Agent”，原 Host 派活／详细计划、任务依赖与容量调度、专家咨询和交付检查保留并接入唯一统筹路径。旧开关耦合消息包装和 autoOrchestration，整合必须接通入口、独立批准，不能删按钮后失去编排，也不能隐式自动批准。

普通参会者按设备＋Agent 稳定定位，重复邀请不新增；一个成员可以关联多个独立任务，各任务仍有自己的执行上下文／工作区。完整任务内的修改、测试和修正连续完成，并发上限约束同时执行数而非可保存对话数；已有原生对话仍按明确身份接续，不默认承接该 Agent 的所有任务。当前新共享执行已按任务保存 thread，普通共享参会交流尚未完整接通。T42–T43 为待实现与待运行要求，本轮仅更新文档；多任务成员的补充归属已在 Q98 确认，见下节。

### 11.9 Q98：讨论与任务补充的明确路由

普通 @ 保持会议交流；任务补充通过任务卡或聊天中明确关联该任务，再进入指定执行上下文，不以最近任务或同品牌名称猜测，不广播到所有任务。复用现有 task.control:supplement／停止后继续能力，新增群聊任务关联与原界面适配；保存补充不等于已执行，A 离线仅保存，停止后不自动恢复。既有原生对话点名仍保持独立明确路由。T44 待实现与运行。

### 11.10 Q99：共享中断范围

用户确认共享会议底部中断区分 Host 当前回复、指定任务与本会议全部当前执行，全部范围再次确认，沿用真实退出核对；其他会议和未选定桌面独立工作不受影响。不能直接复用原本地全 HostGroup 中断，原单机不冲突行为保留，T45 待实施／运行。Q100 最终确认保留执行期间的独立专家交流，日常仍由 Host 统筹；会议讨论不并入正在执行的任务对话，不放宽原生同对话串行规则，跨设备关联仍需适配与验收。
