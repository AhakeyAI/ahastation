## 1. 产品目标与首版边界

两台电脑都安装 Station，登录同一个协作账号，通过同一个会议聊天窗口组织工作。会议由一个 Host 统筹，把能独立交付的工作安排给不同设备的本机 Agent，汇总进度、审批、检查和成果。

同一个会议还可以点名另一台电脑已有的 Codex 对话，利用它原来的身份、上下文、模型和权限继续执行。桌面和 Station 共用这条对话的执行顺序：旧轮次真正完成或停止后，Station 已提交的接续指令自动开始；用户停止 Station 任务后则必须明确继续。

| 首版必须完成 | 首版明确不做或后续优化 |
| --- | --- |
| 同账号多设备、Station 设置内接入 | 跨账号团队和成员权限体系 |
| Codex 新任务执行、已有对话接续两条链路 | 其他正式 Agent 的全部生产验收 |
| 多 Agent 统一接口及非模型测试适配器验证 | 通过空接口声称已支持所有 Agent |
| 手动／自动分配、计划批准分开控制 | 把每条消息或每个步骤拆成独立任务 |
| 已接任务在原执行设备核对和恢复 | 已接任务自动或手动跨设备迁移 |
| 创建会议的设备固定承担协调职责 | 手动或自动移交协调设备 |
| 一个主要代码项目，可另选用户资料仓库 | 多个代码仓库的自动联动 |
| 普通 Git 传选定文件、准确版本、成果分支与 PR | Git LFS、大文件专用链路、Hub 附件中转 |
| 同一原生对话串行；不同对话可按名额并行 | 默认往同一原生对话排多个独立业务任务 |
| 停止后释放执行资源并保留任务与成果 | 单独设置表示放弃整个交付的“取消任务” |
| Windows ↔ Windows 首轮实机验收 | 首轮同时完成所有平台实机与安装包验收 |

保留现有单机会议、任务和其他 Agent 的本机功能，以及 Linux／macOS 的兼容结构。上述延期项不能通过删掉旧功能来实现。

本轮要完成整个 Station 的增量改造。原先新成员负责的设备接入／管理、Agent 准备、项目绑定与本机授权，以及对应生产接口、持久化、迁移、界面和测试全部纳入，不能因为已有四项契约而跳过；原两人分工不再形成前置等待。

## 2. 用户使用流程

### 2.1 两台电脑准备

1. 安装同版本 Station，登录同一个协作账号。
2. 自动注册本机设备并允许命名；首次接入默认不接收工作。
3. 自动识别并复用本机 Codex／Agent 配置和登录，首次明确允许哪些 Agent 接收协作工作、开启接收并设置并发；正常显示可用，缺项才引导原配置入口。
4. A 从首页选择／添加工作项目或本机目录及 Host（沿用默认）创建会议，也可创建不选用户目录的纯文字会议；已有会议直接恢复，无需重选。B 可直接打开同账号既有会议查看／交流，不另创建 Host，不强制弹前台。
5. 涉及文件时再选择用户指定的仓库项目及本机已有副本或克隆位置，按需要检查本机 Git／GitHub 授权；普通目录按其本机授权处理，跨设备文件仍经用户指定资料仓库传递。选项目可就地补配置，不要求先去设置填完所有表单。
6. 各执行设备在首次读取／修改项目文件或执行相应操作前确认自己的目录、任务工作区、Agent 和权限，已有有效绑定复用。A 的路径不能直接当成 B 的目录；未绑定时可交流，不能执行文件任务。
7. A 在原参与者入口选入已允许使用的设备／Agent；本机也须明确勾选参与。B 不逐会议重复确认全设备接收，但承接具体任务仍按项目、权限、能力和名额核验。

普通用户通过 Station 完成这些操作，无需单独启动 Bridge 或输入配对码。Bridge 的执行与兼容能力可以作为内部组件复用，独立 Bridge 窗口不再是新流程的必经入口。

安装包提供内部接收组件与运行时；Git、GitHub 及 Codex 登录按所选功能检查，缺项提供安装或登录指引。已有 Codex 桌面用户不手动选择 CLI 路径，新任务所需内部组件由安装包提供；首版不开发第三方系统工具自动安装器，不要求普通用户手工启动 Python 脚本、npm 开发服务、Docker 或 MySQL。

注册、连接、接收、项目、Agent 和名额分别核验且可查看；正常界面用简短可用摘要，缺项给具体原因，不要求用户逐项填写技术状态，也不能把“已配置”当所有能力均已就绪。

### 2.2 Host 拆分并分配新任务

1. 用户在会议提出目标，Host 澄清资源、操作和成果要求。
2. 一个任务对应完整交付，包括相关文件修改、必要测试和说明。只有可独立交付的工作才拆分。
3. 默认用户批准计划；用户也可显式开启授权范围内自动批准计划。
4. 手动分配由用户选设备和 Agent；自动分配由 Host 从会议已选入且就绪、有授权的设备选择。2026-10-22 补充确认：调度器核验条件后执行 Host 已展示的安排，不静默换电脑；目标暂不可用时显示等待，必要调整由 Host 明确提出并按既定计划批准规则处理。已有原生对话不因自动分配而被默认选中。
5. 协调者发出稳定身份的任务；执行设备再次检查授权、保存任务并确认接收。
6. 执行设备准备独立工作区，调用本机 Agent，回传真实阶段、必要交互和结果。
7. 提交成果、检查与会议内集成通过后，依赖任务再使用对应已验证版本。

各设备本机登录及授权继续有效，开启自动分配不扩大任何设备权限。

审批动线澄清（Q101）：默认在 Station 的计划审阅处一次批准整份计划，再按获准安排派发；不是分发后逐个去 Agent 对话批准业务任务。B 已开启接收且授权有效时不重复点接收／开始。执行中若 Agent 提出工具审批，已适配请求在所属会议／任务内集中显示，A／B 可处理；不能远程答复的原生交互明确指引对应桌面。自动批准计划不等于批量批准工具或扩大本机授权，详见第 7 节。

### 2.3 接续已有 Codex 对话

1. B 开放允许发现的目录，目录内已有对话可被同账号发现，无需逐对话到 B 开启。
2. A 查看引用的标题、项目和可用状态，选择加入会议后按需加载该对话历史；桌面端此后产生的新消息与结果持续同步到该对话详情，标明来源，不默认同步其他未选对话的完整正文。
3. 点名目标为“设备＋具体原生对话”，保持相同原生身份和工作目录，不新建替代对话。
4. 原生模型、审批设置和权限保持；原生完全访问必须先得到 B 的本机明确授权。
5. 桌面正在执行时，Station 保存接续请求并显示等待；确认旧轮次真实退出后才交接。
6. 普通点名默认自由交流；需要正式交付管理时明确建立或关联业务任务，不把每条消息自动建成任务。
7. Host 可以了解点名消息和结果，不对同一指令再拆分派发一次。

Q90 已确认：该对话在会议中标为远程接续关联对象，主聊天展示本次指令、状态和结果摘要；所选原历史及桌面后续消息在对话详情查看，不自动灌入其他参会 Agent 的模型上下文。其他 Agent 通过明确引用或任务所需摘要获取相关内容。

同一对话同时只加入一个共享会议。换会议前先停止相关执行并核对，再明确移出和加入，保留原任务、对话和成果。

### 2.4 在原会议主界面完成多设备协作（2026-10-22 确认）

用户要求在原有同一个会议窗口中邀请其他电脑、分配任务和查看结果；候选版独立“共享会议”面板不是目标使用流程。多设备协作应作为原会议能力的扩展，保留现有“会议／任务”主界面，不要求用户另进一套共享会议和任务系统。

- 原会议的参与者入口可以查看并选入同账号已就绪设备及其允许的 Agent，也可以明确选择已授权的原生对话；设备、Agent 与原生对话须区分展示。
- Q91–Q92 已确认：新建保留项目／目录与 Host 选择，加入既有会议不重复选择 Host；项目未绑定的设备可先交流，文件操作前再在对应设备确认本机绑定。进入会议、参会 Agent 就绪和具体项目执行就绪分别表达。
- Q93 已确认普通新参会 Agent 按需通过会议背景摘要了解当前目标、计划、关键决定和相关成果，再按需取原消息／共享资料；加入本身不自动调用模型或完整读取全部历史。这是普通参会设计，不与已有原生远控对话混为一条链路。
- Q95 已确认普通消息默认由 Host 回应，@ 由指定对象回应，Host 可主动咨询专家；不让所有 Agent 因每条群聊自动回复。任务进度、结果和审批仍可主动回报，原独立批准规则不受“多 Agent”开关隐式覆盖。
- Q96 已确认正常会议不再额外要求开启“多 Agent”。原 Host 派活、详细计划、Worker 调度、专家咨询与交付检查保留并接入统一流程；批准策略独立，不能随邀请或协作开关隐式自动批准。
- Q97 已确认普通成员以设备＋Agent 保持稳定身份；重复邀请定位已有成员，不按任务数增加席位。一个成员可关联多个独立任务及各自执行上下文／工作区；单个完整任务连续完成内部修改、测试和修正。成员的会议交流、各任务执行及明确选中的原生对话分别管理，并发名额不等于持久对话数量。
- Q98 已确认普通 @ 默认进入成员的会议讨论；任务补充通过具体任务卡或聊天中明确关联该任务，进入相应执行上下文。不按最近任务猜测、不向成员全部任务广播，无法确定时澄清。沿用原停止、离线保存和投递核对规则，不能将保存成功显示成已经执行。
- Q99 已确认共享会议底部中断先明确范围：停止 Host 当前回复、停止指定任务或停止本会议全部当前执行；全部范围再确认，任务卡保留单任务停止，不影响其他会议及未选定桌面独立工作。原停止核对与记录保留规则不变，原单机不冲突行为保留。
- Q100 已确认保留原有“Worker 执行时仍可与独立参会专家交流”的能力；日常仍由 Host 统筹，主动 @ 专家是可选操作。专家交流不直接插入正在执行的任务对话，不保证取得任务全部实时上下文，既有原生对话仍串行接续。
- 会议聊天承载用户目标、同一位 Host 的澄清、拆分计划与关键进展；原“任务”界面展示本机及远端任务，同一业务任务从计划、执行到成果保持相同身份。
- 延续原会议 Host 的统筹、计划和批准流程。一个会议只有一个拆分与派发权威，不因加入远端设备另起一位对同一目标重复处理的 Host。共享传输和本机执行能力接到该流程后面。
- 拆分以可独立完整交付为依据；计划和结果须让用户读懂，不要求阅读 JSON、内部设备编号或原始接口字段。
- 2026-10-22 Q78 修正 Q74：本机可在执行设备列表中由用户勾选，不自动选入、不默认参与执行，无需另加一个默认开启的专用开关。勾选只是允许成为候选，真正执行仍须经任务分配、计划批准和本机接收、Agent、项目授权及并发条件核验。未勾选时仍可主持和查看，取消参与不自动停止已有任务。
- 2026-10-22 Q75 确认：自动分配保留 Host 明确展示的设备安排，调度器不得静默覆盖。不可用时显示等待或由 Host 明确调整，按既定计划批准规则处理；该规则不扩大为已接任务跨设备迁移。

| Station 界面 | 设置、会议、任务、审批、原生详情、成果查看与手动操作 |
| Station 可信本机运行时 | 本机授权、目录绑定、名额、工作区、Agent 生命周期、真实退出核对 |
| 唯一协调者 | 统一计划、任务拆分与分配、检查和返工组织 |
| Hub | 账号隔离、设备目录、项目共享身份、会议状态、任务／审批／事件和文件引用 |
| GitHub | 输入、成果文件、准确提交、独立分支和 PR |
| Agent 适配器 | 编译执行要求，声明能力，映射事件、审批、停止、核对及恢复 |

数据库由 Hub 访问。Station 不直接连接云端 MySQL，不下发 MySQL 密码或 Hub 服务密钥。

已有链路是 Station 通过 HTTP 提交／轮询、独立 Bridge 通过 WSS 接收。新共享会议尚未接入，不能把旧链路当成两台 Station 已有统一会议通道。

技术建议：双端采用同一套平台无关协议，WSS 传实时事件，HTTP 负责登录、快照、补拉和幂等控制请求。连接方式按职责定义，不按 Linux／Windows 分出两套业务逻辑；协议细节须在实现中与云端实际部署核对。

完整的发送、接收、持久确认、断线补拉、单实例部署边界及设备／项目模块清单见 [通信与整体改造范围](COMMUNICATION_AND_SCOPE.md)。长连接只是通知通道，生产快照、事件、业务任务与本机执行核对必须同时实现。

## 4. 领域身份、契约与状态

| 概念 | 边界 |
| --- | --- |
| 协作账号 | 同一用户的设备归属，不是模型或 GitHub 登录 |
| 设备 | 稳定身份，名称可改；Agent 是其能力，不等于设备 |
| 会议 | 统一目标、聊天、计划和任务；创建者设备固定协调 |
| 仓库项目 | 用户指定的 GitHub 仓库及可选子目录 |
| 本机绑定 | 项目在某台电脑上的副本、工作区位置和授权 |
| 业务任务 | 完整交付；补充、多轮执行、验收前返工仍属于它 |
| 执行尝试／原生轮次 | 任务内部执行记录，不据此强迫用户新建任务 |
| 传输请求 | 网络投递与幂等身份，不等于业务任务 |
| 原生对话 | Codex 自己维护的上下文，不由 Hub 复制成替代对话 |
| 文件引用 | 仓库、准确提交号和相对路径，不使用远端绝对路径传文件 |

四项公共契约已存在：设备信息、项目信息、本机授权核验、状态变更通知。继续以同源 Schema、TS／Python 校验、样例和测试约束生产者与消费者。

新需求必须补充会议、业务任务、执行尝试、传输请求、原生对话／轮次之间的关联，以及审批、文件引用、名额和退出证据。现有项目契约必填 GitHub；非仓库目录／纯文本需显式扩展资源模型，不删除原来的仓库校验来假装兼容。

执行、交付、检查／集成、最终验收分别记录。至少应区分：

- 等待分配／接收、等待名额、等待桌面接续、执行中、等待审批。
- 停止请求中、停止未确认、已停止、原设备待恢复。
- 执行完成、交付待处理、成果已可获取、待检查／返工、会议集成已验证。
- 用户最终验收、最终 PR 合并状态。

事件和状态必须能够核对重复、迟到和旧执行的结果。旧 attempt、旧连接或旧审批不得覆盖当前任务；恢复不重放已经产生副作用的执行。

## 5. 授权、并发、停止与恢复

### 5.1 本机授权和执行名额

- 共享项目身份不授予本机路径操作权。A、B 可以使用不同本机路径。
- 目录可见、允许接续、实际原生权限与本机权限上限分别核验。
- 本机明确允许后可接续完全访问会话；不静默降级原生权限，也不从远端自动提权。
- 本机任务并发上限默认一、可调，跨会议共用；Host 统筹不计这个任务名额。
- 不同对话可按名额并行，同一对话串行；等待桌面接续、已确认停止不占执行名额。
- 已经占用资源但停止未确认时不得提前释放。拿到 OS 锁或收到停止 ACK 不能单独证明退出。
- 关闭接收只拒绝新工作，已接任务继续且仍可查看、停止。撤销项目／Agent 授权须停止受影响执行并禁止继续，保留成果。
- 不安排两个任务同时写同一物理目录；并行独立任务用独立工作区和分支。

### 5.2 停止和继续

首版统一使用“停止任务”，没有必须放弃或删除任务才能释放资源的流程。

1. 只停止明确选定任务的当前执行；确认实际停止后释放执行资源和并发。
2. 保留原对话、任务记录、工作区、文件和提交，其他独立任务正常运行。
3. 依赖其结果的工作等待继续或重新安排；停止后的任务不自动恢复。
4. 用户明确继续时显示未执行补充，允许编辑或忽略，核对已投递内容后继续原任务。
5. Station 等待桌面时，停止该 Station 任务不打断桌面当前轮次；要停止桌面轮次必须明确选中它。

同账号且已授权时，Station 可以明确停止桌面发起的轮次，桌面也可以停止 Station 发起的轮次；只作用于选定对话的精确轮次，并核对实际退出。若被停止的是 Station 当前任务，无论从哪端停止，都保留任务并等待用户明确继续。

桌面旧轮次完成或停止后自动接续已经提交的 Station 指令，与主动停止 Station 任务后等待明确继续，是两个不同场景。

### 5.3 离线和异常

“已接收”以执行端核验授权、保存任务并确认接收为界，Hub 收到或发出消息不足以证明。

| 情况 | 首版行为 |
| --- | --- |
| A 离线，B 已接任务正在执行 | B 继续并保存结果 |
| A 离线，B 已接任务尚未启动 | 授权／并发条件满足时可启动 |
| A 离线，新拆分、新分配、新补充或继续请求 | 不新增执行；输入可保存，等待 A 恢复 |
| A 离线，停止或 B 本机处理已接任务审批 | 仍允许 |
| B 断线或结果超时 | 核对原任务，不能直接判失败后重跑 |
| 原任务实际仍运行／已完成 | 分别继续跟踪／补收结果 |
| 是否已执行或停止无法确认 | 保持待核对，不另起一份，不提前释放占用 |
| 原设备恢复 | 核对原任务和原生执行，再恢复控制；主动停止的仍需明确继续 |
| 已接任务要换到另一台电脑 | 首版不实现，后续优化 |

B 在会议外独立使用本机 Codex 桌面不受 A 离线限制。已接任务的长期业务记录不能仅寄存在会定期清理的传输 journal 中。

### 5.4 窗口与进程生命周期

关闭主窗默认后台运行；返回首页或关闭共享会议标签只暂离界面，可从会议列表回来。

显式退出 Station 才提示并停止本机 Station 执行，核对后退出；不关闭 Codex 桌面，不停止桌面独立发起的工作，不把其他设备任务标失败。未确认停止时显示原因，用户可等待或强退；强退不能伪造资源释放，恢复后继续核对。

退出协作账号时也按停止规则处理本机 Station 执行并保留成果，不退出模型或 GitHub 账号。凭证失效时阻止新投递、提示重新登录并保留核对入口，重新登录不自动重跑原任务；重装或换电脑重新接入并确认本机授权，首版不新增跨设备身份或任务迁移向导。

## 6. GitHub 文件与交付

所有代码仓库和资料仓库由用户指定。纯文字交流无需仓库；跨设备文件必须先成为双方可读取的 GitHub 提交。

1. A 选择需要共享的输入，提交到资料分支并推送，不自动上传整个项目。
2. 任务分别记录代码工作基线和输入文件引用。输入资料提交不自动成为代码成果 PR 的内容。
3. B 获取准确提交中的文件；仅存在 A 本机、未提交或未推送的内容显示未共享。
4. 仓库任务从明确代码基线建立独立工作区／任务分支。普通研究任务可在普通授权目录执行，选定输入和成果通过资料仓库传递。
5. 成果提交、推送并创建 PR，回传提交号、成果文件清单、测试和说明。
6. 推送／PR 失败保留工作区和提交，显示交付待处理，核对后补交付，不重跑整个任务或重复建 PR。
7. A 在 PR 未合并时即可按提交查看、获取真实成果，默认取到独立目录。应用到当前工作区另行明确选择并检查已有修改。

原生对话保持原 cwd 和已有修改，不自动清理、暂存或切换分支。交付前检查混杂改动；不能可靠分离本任务成果时等待用户确认范围，不直接提交整个目录。

### 6.1 会议内集成和最终合并

Host 检查后，自动把合格代码成果整合到会议专用分支，组合验证通过才放行代码依赖任务，无需用户逐个合并 PR。冲突或验证失败时保留最近通过验证的会议版本，组织相关原任务修复。

前序成果发生修改后，Host 将受影响的既有后继成果标记为待重新验证或返工，保留旧提交和检查记录，不把旧结果当成最新结果验收；无关任务继续。后继成果所依据的版本及复验结果须能追溯。

技术建议采用两级 PR：任务分支面向会议集成分支，会议汇总成果面向用户指定最终目标分支。输入分支保持独立；这属于待整体确认的实现组织方式，不表示已创建任何分支或 PR。

最终验收前的同目标修正仍归原任务；最终验收后的追加／修复建立关联原成果的后续任务，保留验收历史。

最终验收不自动合并代码。首版在 Station 展示 PR 链接，由用户到 GitHub 审查并完成最终合并，再核对更新状态。

## 7. 审批、进度与成果界面

- 2026-10-22 确认：将多设备邀请、计划、任务进度和成果整合进原会议与“任务”主界面；独立共享面板不再作为正式使用的必经入口。计划、任务和成果使用面向用户的中文展示，JSON 与完整日志只作为可展开的诊断详情。
- 沿用原有计划审阅、会议任务表、任务看板、任务检查器和交付详情的设计并扩展设备信息；“可读卡片”是可读性的描述，不是要求再造一套卡片产品或替换现有表格、看板和详情组件。
- 普通会议消息交给 Host；明确点名已有原生对话直接路由，不重复派发。
- 主聊天展示关键变化；任务卡展示设备、Agent／原生对话、阶段、等待原因和更新时间。
- Host 提案必须清楚展示各任务的目标、完整交付、执行设备和 Agent、依赖及计划状态。明确区分“建议分配”“已发出”“已接收”和“实际执行中”，不能将模型的预选目标直接标为正在执行。
- 延续原计划说明的设计，展示拆分依据与完整交付之间的关系；不会因电脑数量增加就强行增加任务。若只是同一交付的连续工作步骤，保留一个任务。
- 计划批准前与执行后都能看清“哪台电脑上的哪个 Agent／原生对话正在做哪项任务”；本机明确标注为本机。任务详情可从参与者和任务列表定位，返回原会议时不产生另一份任务或重新发出指令。
- 完整输出、命令、测试和选定原生对话历史放详情，持续同步该对话从桌面端产生的新消息与结果并标明来源；不凭估计显示百分比。
- 工具审批在两端 Station 展示并可答复，也保留 Codex 桌面入口。同一请求只接受一次有效决定，已处理／过期或旧执行的请求失效。
- 工具审批不能扩大 B 的授权。A 离线时 B 可处理已接任务本机审批。
- 能力不支持时说明原因和可用处理入口，不假报完成；工具批准不等于所有原生问答交互均已支持。
- 成果卡展示摘要、测试结果、文件清单、准确提交及 PR，允许打开／获取。
- 明确区分执行已结束、成果已上传、检查通过、会议集成通过、最终验收与最终合并。
