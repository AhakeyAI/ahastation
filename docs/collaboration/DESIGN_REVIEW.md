## 第一轮已确认

1. 主线是一个共同聊天窗口组织多台电脑协作：两台电脑安装 Station、加入同一会议，由 Host 拆分任务，支持手动／自动分配，各设备调用本机 Agent 执行，在会议汇总进度和结果。
2. 同一会议还要支持选择并点名另一台电脑已有的 Codex 对话，保留该原生会话的上下文继续执行。这不是新建替代对话。
3. 同一条 Codex 对话允许桌面端和 Station 操作，但要统一协调执行顺序。桌面完成或停止后，Station 可直接接续，避免重复执行或会话冲突。具体排队、公平性和停止范围尚未确认。
4. 首版只做同账号多设备，不扩展到不同用户的团队权限。
5. 基于现有 AhaStation 增量开发，保留单机会议和任务；普通用户通过 Station 设置完成设备接入。
6. 沿用微信云托管 Hub 负责跨公网的身份、设备和协作信息传递；本机 Station 负责本机授权和 Agent 执行；GitHub 负责仓库、分支、提交和 PR；数据库由 Hub 管理和访问。

## 第二轮已确认

对应访谈 Q5–Q10：

1. A、B 任意一端均可在同一会议发言、点名、提出和调整任务；涉及某设备的目录和执行权限仍由该设备授权。
2. 同一会议由同一位主持智能体、一份计划和调度流程统筹，默认创建会议的电脑承载协调流程。术语中使用“协调者”区分统筹智能体、“协调设备”区分其承载电脑。
3. 明确区分新任务执行的“设备＋Agent”目标和原生会话接续的“设备＋具体 Codex 对话”目标；同一指令不同时走两条执行路径。自动分配默认使用新任务能力，已有原生对话需要明确选择或授权参与。
4. 执行顺序协调边界是同一条 Codex 原生对话：桌面端和 Station 不抢占当前轮次，旧轮次完成或停止并确认实际结束后自动接续；不同原生对话应独立执行，不设全局串行约束。第三轮进一步收紧了任务粒度：不因此默认把多个独立任务连续排入同一原生对话，详见下一节。
5. 认可共同聊天默认汇总会议消息、任务、进度和结果，原生历史与桌面新增内容在对话详情中查看的分层方向。用户明确要求后续再问进度与结果的具体显示效果，目前不设计相关 UI 细节。
6. 首版还要支持无需绑定 GitHub 仓库的纯聊天、研究等工作；写文件仍需本机授权，Git 分支／PR 流程用于仓库工作。用户明确要求后续专门讨论如何区分任务类型，目前不确定分类枚举或判定方式。

## 第三轮已确认及修正

对应访谈 Q11–Q16。Q12、Q13 的答复是对任务粒度及并行方式的修正，不是确认此前提出的多任务队列方案。

1. 同账号、原生会话已授权后，允许 Station 显式停止桌面端发起的当前轮次，也允许桌面端停止 Station 发起的当前轮次；目标必须是明确选定的原生会话／轮次，不连带影响其他对话。当前代码的跨来源 owner 限制需要后续按此新需求调整，不能误称已经支持。
2. 一个任务对应一次完整交付。同一目标所需的多文件修改、必要测试和结果说明，应由 Codex 在该任务中连续完成，不按步骤逐个新建任务。
3. Host 只在工作可独立交付、适合分派给不同设备或 Agent 时拆分。并行的独立任务各用独立工作区和分支，不安排两个任务同时写同一物理目录。无需仓库的工作具体如何组织，随任务类型专题继续确认，不据此强制所有研究任务创建 Git 分支。
4. 首版不默认给同一条 Codex 会话连续安排多个独立任务。之前提出的“停止①后自动开始②”等多任务队列方案未被采纳；排队、取消等待项、暂停后续等规则暂缓。已经确认的桌面／Station 同会话交接保留，需要区分同任务后续要求与新的独立任务。
5. 断线或超时后先核对原任务：仍在执行就跟踪，已完成就补结果，无法确认就保持状态待核对；不得因为网络重试重复执行。
6. 协调设备 A 离线时，B 已接任务继续执行并保存结果，Host 新拆分／分配暂停；A 恢复后先核对状态。首版不自动在 B 启动第二协调者。直接点名已有原生会话在此期间能否独立工作尚未确认。
7. B 主动开启接收并确认 Agent、目录、权限后，范围内任务无需再逐项点击接收／开始。Agent 原有工具审批保留；越界暂停或拒绝，A 的自动分配不能扩大 B 的权限。

## 第五轮已确认及修正

## 第六轮已确认及修正

对应访谈 Q26–Q30。Q29 的答复选择 GitHub 统一文件传递，替代此前问题中提出的附件中转服务方案，不能仍将后者列为首版需求。

## 第七轮已确认及修正

对应访谈 Q31–Q34。用户在 Q31 额外明确：所有 GitHub 仓库都由用户指定，不由软件统一设置。

1. 纯文字交流无需仓库；需要跨设备传递文件时，使用用户指定并已授权的 GitHub 仓库。研究、文档等任务仍可在普通授权任务目录执行，由 Station 将选定输入和成果提交到所选资料仓库，不要求将执行目录本身改成 Git 仓库，也不假设存在软件统一的中转仓库。
2. 输入资料默认放资料分支并引用准确提交；成果 PR 只包含应交付修改。输入资料本身也应成为项目文件时，再明确纳入成果 PR，不因作为参考就自动进入最终目标分支。
3. Host 检查通过后，可自动将前序代码成果整合到会议专用集成分支，组合验证通过再放行代码依赖任务，无需逐项等待人工合并 PR。这细化第六轮 Q28：会议工作分支内可自动整合，最终合入主分支或既定目标分支仍需用户批准；不能把会议内集成通过当作最终验收或已发布。
4. 首版使用普通 Git 传文件，大文件支持后续增加。不自动启用 Git LFS，也不因普通 Git 限制而改走首版未授权的其他传输通道；超限资料须明确显示未共享，不能把本机存在或仅上传指针当作远端已经取得实际文件。

## 第八轮已确认

对应访谈 Q35–Q39，用户逐项确认建议：

5. Agent 已执行完成但推送或 PR 创建失败时，保留工作区和已有提交，显示执行完成、交付待处理。恢复时先核对远端，再补交付；不重跑整个任务，不重复创建 PR。交付未完成时不向依赖任务宣告成果就绪，依赖仍需对应的成果可获取与验证条件。

3. 首版不另设“取消任务”。停止任务应结束其当前执行，确认实际停止后释放执行资源和并发名额，同时保留 Codex 原对话、任务记录、已有文件和提交；用户不必放弃或删除任务来释放资源。其他独立任务正常进行，依赖该任务结果的后续工作等待继续或重新安排。
4. 停止后的任务不自动恢复，必须由用户明确选择继续；待补充要求不能绕过停止状态触发新执行。此前已经确认的桌面旧轮次完成或停止后接续 Station 已提交指令仍保留，需要区分“旧桌面轮次结束”和“用户停止该 Station 任务”，不混用状态或操作目标。
5. 以用户对整个会议目标的最终验收作为本次交付结束边界。最终验收前同一目标的修正仍归原业务任务，即使 Host 已检查通过或成果已进入会议集成分支；最终验收后的追加或修复建立关联原成果的后续任务，保留原验收记录，也可明确选择原 Codex 对话执行。
6. 集成冲突或组合验证失败时保留最近通过验证的会议版本，暂停受影响的依赖任务，由 Host 在授权范围内组织相关原任务修复、再检查和集成。失败成果不能放行，不要求用户每次亲自处理冲突；超出授权范围仍遵循既定授权规则。

### Q70–Q73：原会议整合、可读性、Host 拆分与本机分配

用户本轮提出的四项问题，依次编号为 Q70–Q73。

**Q70：为什么共享会议单独做入口，能否在原会议邀请电脑、分配任务和看结果？**

- 用户已明确的期望：在同一个原会议窗口完成上述流程，不另用一套共享会议界面。
- 源码事实：App.tsx 在首页及会议页面单独挂载 SharedMeetings；独立面板并非通信协议或授权的技术必要条件。它是当前候选实现的呈现方式，未达到用户期待的完整集成。
- 需求结论：多设备是原会议的扩展；统一参与者、聊天、计划、任务和成果，保留同一会议唯一 Host。具体视觉布局在后续 UI 设计中细化。

**Q71：分配和结果难以阅读，能否使用原会议／任务主界面，现有接口能否供 UI 使用？**

- 用户已明确的期望：整合到原界面，清楚表达任务与结果；后续 UI 优化要能够复用已有服务。
- 源码事实：preload 的 collaboration.request／onChanged 已供受信 Station 页面调用；status 提供快照，command 提供受限会议／消息／计划／任务／审批操作，另有本机授权和交付入口。当前 SharedMeetings 已在使用这些接口，原 TasksView 则读取 CrossProjectTasks，尚未映射新共享实体。
- 实施方向：保留现有通信、鉴权和持久化能力，新增统一的前端状态投影与命令适配，复用原会议和任务组件。不能在两个界面各维护一份独立计划／任务，不能将远端任务伪造成原 Orchestrator 的本机执行任务。
- 展示要求：计划给出目标、交付内容、执行设备＋Agent、依赖和状态；执行卡区分提议分配、已接收与执行中；成果显示摘要、测试、文件／提交／PR。JSON 与原始日志只在诊断详情查看。

**Q72：拆分是否遵循原设计由 Host 完成，为什么看不清任务给谁？**

- 用户已明确的期望：沿用原 Host 拆分设计，只拆可独立完整交付的工作，并清楚展示分工与执行。
- 源码事实：新 SharedCoordinator 实际调用 Codex 模型、按共享快照生成 station-plan；不是用随机数切分。但它与原 Orchestrator 的 plan_meeting／proposePlan／批准计划流程并列，未接回同一个原会议 Host。
- 另一项事实：自动分配会过滤在线、接收、能力、项目和名额后按 activeTasks 取首个设备，覆盖 Host 提案中的 targetDeviceId。模型提出任务与调度器选择设备是不同步骤；当前还缺少解释提案与实际目标差异的清晰界面。
- 需求结论：原会议 Host 继续理解目标并产出唯一可读计划；分配是独立于任务拆分的执行安排，不能靠第二位 Host 或另一份计划绕开原流程。自动调整目标的规则已在后续 Q75 答复中确认，见下文。

**Q73：当前会把任务分配给本机吗？**

### Q76–Q78：原界面与 Host 机制解释、本机规则修正

**Q76：整合是否意味着不用复用，原有会议和任务界面怎样设计？**

用户追问技术和产品含义，不能将其解读成要求删除已有接口。核查事实如下：

| 原有组件 | 已有设计 | 多设备需要补充 |

解释与方案：整合本身就包括复用原界面和有价值的底层能力；原有表现组件与新增设备通信／鉴权／持久化分别保留，连接共享数据与动作。移除正常流程对独立共享面板的依赖、收敛两套统筹权，不等于把新增 Hub 或原有组件都删除。“可读卡片”不要求把现有任务表、看板和详情全部另做一套。

**Q77：新增共享 Host 怎样调用模型，与原 Host 拆分／交付的区别是什么？**

- 原 Host：读取原会议的上下文与成员，经 plan_meeting／delegate_task，或 provider-neutral 的 meeting-command 进入同一 Orchestrator 计划流程；详细计划含 goal／approach／steps／risks／openQuestions 与完整任务 brief，经批准进入 WorkerScheduler。Worker 以结构化 WorkReport 交付，按实际路径进入验证、冻结、审查和会议集成；不是所有模式都自动集成或都需要人工逐任务接受。
- 新 SharedCoordinator：在协调电脑单独创建／恢复 Codex thread，以只读统筹提示词、裁剪过的共享快照和用户消息调用本机 Codex；模型输出 station-plan JSON 任务数组，经字段／权限校验成为 Hub 的 plan.propose。批准后由 StationService 和 Hub 派发给选定设备；没有调用原 Orchestrator.proposePlan。
- 新交付：StationService 另行生成摘要、文件、commit／branch／PR，再按配置执行组合验证；tests 多为字符串说明，不是原结构化 WorkReport 流程。SharedCoordinator 未调用原 DeliveryHarness／CoordinatorReviewDriver，输入任务摘要还省略 output／evidence，不能声称原 Host 已自动深审每项远端成果。
- 整合方向：保留原 Host 的完整计划、批准和交付检查语义，扩展设备选择／执行路由，保留新增网络、接收和恢复能力。原提示中的“复杂多步”也需遵守已确认规则：只有独立完整交付才拆任务，不能按步骤硬拆。此处说明差距和方案，尚未修改实现。

核查过程中另见原计划正文编辑的提交缺口：PlanMeetingModal 的 draftBrief 可修改，但 onSubmit 目前只传任务数组；计划容量使用固定值 4。记为复用时须核验的源码问题，不误称原计划所有编辑都已正确保存，也不据此扩展新的产品范围。

**Q78：本机选择更正，替代 Q74**

用户原话：“也不是自动让本机执行任务，现有的实现是可以勾选本机执行吗，如果是的话我理解错你的提问了，修改为可以勾选本机进行执行即可”。

**Q80：设置流程能否简化为登录、GitHub、仓库绑定？**

现有 RemoteControlSettings 与 CollaborationSettings 共享登录基础，却连续暴露旧配对和新设备配置，导致重复概念。正常 Station ↔ Station 流程不要求独立 Bridge；旧配对、恢复码、撤销、LAN 和服务地址保留高级入口。GitHub 登录是本机权限，不等于 Station 账号或 Codex 账号。当前 checkGithub 主要检查 origin／读取权限，不包含完整浏览器登录界面；需补状态探测和引导，不能把原型按钮当作已有可直接调用的登录接口。

**Q81：聊天就是群聊，不需要收件人框，复用 @。**

原型已移除发言目标下拉框，提供 @ 候选、键盘选择、普通群聊、执行 Agent 补充和原生对话接续示意。原型对多目标操作只提示演示范围，不据此新增正式产品的点名数量限制；正式实现沿用原有解析语义并补歧义测试。

### Q83–Q85：Agent 准备、参会展示及运行中邀请

**Q83（已确认）：保留独立 Agent 设置与协作就绪摘要。**

**Q84（已确认过渡方案）：按设备与 Agent 展示，旧适配器内部保留至迁移验收。**

用户先同意按“设备 · Agent”展示，并追问保留 Pocket Vibe 的必要性和移除影响。在了解源码依赖后明确答复：“是，按这个过渡方案处理，旧适配器先内部保留，迁移验收后再移除。”因此确认过渡保留，不承诺永久维护两套入口，也不授权现在直接删除。

源码事实：Pocket Vibe 在原系统中是远端接入 backend，不是一种模型。registry.ts 仍注册 PocketVibeBackend；Orchestrator.addHost 和 sessions IPC 将已有远端原生目标绑定到 backendId=pocket-vibe，恢复旧会议也按该标识重建远端成员。remote-control.ts 还存在旧 LAN 配置读取路径。因此隐藏产品名称，与删除旧接入适配器不是同一操作。

若当前直接移除适配器而未改调用与记录，旧会议远端成员恢复、原生对话邀请／点名、旧 Bridge／LAN 接入会受影响；保存的数据不因此自动被删除。新 StationService 的设备协作是独立的新执行路径，目标设计可以不依赖旧入口，但当前原会议尚未整合，不能把“新路径存在”当作迁移已完成。Hub、协作账号、数据库和原生执行组件不能因名称含 pocket-vibe 就一并清理。

当前决定：正常入口统一使用设备与 Agent／原生对话身份；旧适配器只承担过渡期旧记录、连接和未结束执行的兼容，普通用户无需选择或理解 Pocket Vibe。新链路替代、旧任务核对、记录迁移和恢复验收完成前保留控制入口；验收后再移除不需要的旧适配器。具体待迁移清单和验收证据在实施前核查，不把此项确认视为迁移已经完成。

补充核验：新 StationService 直接使用 CollaborationConnection、Codex／NativeExecution，不调用 PocketVibeSession；因此新双 Station 主流程并非必须长期依赖旧 backend。旧 adapter 的 interrupt／恢复仍操作原 submission 和 turn，并等待 cleanup_confirmed；迁移不能只迁移标题／ID，还需核对旧已投递执行，保留能停止／回收的入口。删除旧 adapter 不会自动删除 MySQL 数据或撤销配对，但旧 Bridge 设备也不会自动变成已注册的新版 Station 设备。

**Q85（已确认）：运行中邀请不自动改派。**

用户接受：新增 Agent 只扩展后续工作的可选参会对象；保留当前 Host、已批准计划和正在执行任务的安排，需要调整时显式修订计划。邀请不等于设备接收、目录授权、计划批准或立即执行，也不自动将新成员变成第二个协调者。

本轮继续只维护设计文档，未修改 Agent、会议或通信运行代码。有关“参会专家自由交流”与“被分配任务的执行者”是否应使用同一个入口但分别管理上下文，仍需下一轮明确，不提前把原有自由交流缩减成仅能补充已分配任务。

#### Agent 能力与邀请方式的只读核验

- 原 BackendSettings 提供 Claude Code、Codex、Kimi、Qoder、OpenCode 等既有本机配置入口，认证方式由各适配器分别支持，并非所有 Agent 都有同一种 OAuth。SideDrawer 据已配置状态和运行时可用性显示邀请入口。
- 原会议中途可邀请；addHost 创建独立 HostGroup，握手本身不自动发欢迎模型轮次。新参会者不自动获得此前全部会议聊天历史；原生对话保留自己的历史。普通参会与正式任务执行不是同一个动作。
- 原 UI 通常按 backendId 去重，底层还有 Host 总数与原生目标重复限制；这尚不是完整的“相同 Codex 可分别来自多台电脑”的参会身份模型。整合时要补设备＋Agent／原生对话身份，保留同一会议唯一协调者。
- 新共享 probe、任务执行与共享 Host 当前正式接通 Codex；file-test 为显式测试开关下的非模型适配器。统一 AgentCapability／ExecutionHandle 接口存在，不代表其他 Agent 已逐一接通审批、停止、恢复及真实双机验收。
- 上述差异是现有源码事实，不新增范围承诺：仍按已确认的 Codex 首版和原本机其他 Agent 功能保留原则推进。
