# collaboration.6 真实双机与 GitHub 验收步骤

本文件是待执行清单。当前候选的本机双进程、隔离 Hub、真实 Electron 和专用真实模型证据，均不能代替以下真实双机／公网／GitHub／原生产档案恢复。

1. 保存 .5 安装包、数据库备份、现有 Hub 配置和设备档案。不要清除 Local State、账号密文或设备密文。生产环境发布仍需另行明确授权，本候选不会自动部署。
2. 在独立 MySQL5.7 演练环境先确认 schema2；schema1 按原01—03流程处理。运维 DDL 身份执行04-add-text-artifacts.sql和05-verify-text-artifacts.sql，保留运行账号DML权限、station_hub账号和原HUB_SECRET。06只核对保留数据的回退前提。不要删除新表、清空历史或用旧备份覆盖新业务。
3. 在 A、B 两台 Windows 安装同一 .6 候选与匹配 Hub。用正常方式登录同一 Station 账号，核对各自设备ID、接收开关和本机授权。只将 B 明确选为执行候选；A 未被选择时只承担原 Host 与协调职责。
4. 创建统一会议，分别验证设备邀请、稳定 @、同名消歧、小屏与缩放、浅深主题。B 的认证或执行错误应归属 B/原任务/原attempt；A 的其他会议仍可工作。打开原错误详情与恢复控件，确认不会被错误顶栏挤掉。
5. 让 Host 基于当前完整计划提出一个 B 执行的纯文字任务，使用 Codex 0.164.0、read-only、inputs=[]。手工批准，确认不会抢先执行或随机改派。输出含长中文、emoji、组合字符和唯一尾标记。对照 B 的完整UTF8、Hub manifest 与 A 获取的全文，逐字节核对byteLength/SHA；不要只查看预览。
6. 在演练环境断开并恢复传输、重启 Hub，确认仍是同一 taskId/attemptId、同一原生对话，不重跑模型补正文。未完整、冲突片、错误SHA、超额或旧attempt不得成为完整交付；B 本机全文仍在。
7. 打开人工检查弹窗，查看全文、实际测试、未执行项及风险。空说明不能提交，快速双击只记一次，失败后说明仍在。打开后切换到新attempt/成果，旧说明必须被拒绝。正常完成后停止仍能核验原成果；实际中断的部分结果和失败测试不能因人工文字被当作通过。
8. 使用“明确修改交付要求”同时修改当前目标与验收条件，检查旧范围、旧成果仍在历史。同一 taskId 在明确继续后才创建新attempt，传递当前要求及本次继续说明；不永久拼接被替代条件。普通补充继续走原补充流程。检查依赖重验和原目录实际退出后才释放资源。
9. F09 受影响档案单独处理：先保留原密文与诊断，区分本地解密失败、服务端认证失效和设备撤销。仅在正常登录可用且用户明确确认授权变化后使用凭据恢复；核对接收已关闭、Agent/目录需重新确认，任务/原对话/已有成果和旧密文历史仍保留。原坏密文初始成因尚未查明，不承诺重登一定找回旧键。
10. 用户需先明确指定专属 GitHub 测试仓库、目标分支与权限。A、B 正常绑定各自本机目录，确认相同准确基线，独立任务在独立工作区/分支执行。选定文件、代码和附件通过该仓库传递，文字通道不承接附件。验证提交、推送、PR、准确成果获取、组合验证及人工验收；不要使用用户未指定的仓库，不自动合并或生产部署。
11. 用户正常 Codex Desktop 接续及公网故障试验，只在当前正常访问方式和明确授权具备时执行。无访问条件记BLOCKED，不改原Codex数据库、history_mode或历史，不向原用户对话发送测试prompt。

记录实际执行的日期、A/B安装版本与载荷SHA、Hub部署来源SHA、数据库版本、原始task/attempt/thread/turn、正文byteLength/SHA和每个检查的结果。日志只保留脱敏信息，不附登录文件、密钥、令牌或完整环境变量。
