# collaboration.3 定向修复升级说明

适用 Station 0.19.0-collaboration.3 与本包 Hub。此次只修复 R1–R4；继续使用现有域名、MySQL 5.7、station_hub、账号、设备、授权、会议、任务、请求去重及事件历史。本包没有生产发布，也不要求重新配对设备。

## 数据库与兼容边界

当前 schema=2 **不需要任何新增 DDL**。Host 失败状态、retryOf、任务 approvedPlanRevision 均保存在现有 collab_entities LONGTEXT；每次计划修订的旧、新值仍留在原有追加事件中。状态派生和计划基线等待不创建重复业务任务或改写已执行字段。保留 HUB_SECRET 和数据库密码，Station 仍只通过 HTTPS/WSS 访问 Hub。

若现有部署尚为 schema=1，先参考随包 MYSQL57_HUB_UPGRADE.md 和 mysql57-upgrade/ 的既有增量材料。这属于之前的协议升级前置条件，不是 .3 新增结构迁移。应用数据库账号保持 DML 权限，不给应用 CREATE/ALTER，不删除或重建 station_hub。

新 Hub capabilities 增加 unified-review-fixes-v1，新 Station 声明 X-Station-Features: unified-meeting-v1,unified-review-fixes-v1。新 Station 要求匹配 Hub 后才启动协作处理。旧 Station 可以继续读取旧兼容状态；账号一旦存在 preparing/failed/retryOf 消息，旧特性请求会收到 426，防止旧客户端消费不认识的恢复状态。旧 Bridge、原生会话及账号接口保留。推荐相关 Station 全部升级，避免旧版仍存在 403 客户端误判。

## 推荐顺序

1. 通过已有管理控制台保存当前镜像版本、非公开配置和 station_hub 完整备份，验证备份能恢复；包含身份、凭据、设备、协作实体、事件和幂等请求。不要把真实配置或备份装入源码包。
2. 先在独立环境解包本 Hub 包，以压缩包根 Dockerfile 构建。保持现有数据库连接与密钥，确认 schema=2；无新增迁移命令。需要维护窗口时沿用 HUB_MAINTENANCE=1，暂停新接单，保留核对、停止、已有结果和重复回执。
3. 验证 /health、/ready。通过正常 Station 身份读取认证后的 /api/collaboration/v2/snapshot，确认两项 capabilities；无认证 401 只能证明路由存在。/api/collaboration/v2/identity 返回原 ownerId/deviceId；X-Station-Device 不匹配会返回认证错误。
4. 升级 Station 到 .3，保持原用户数据和系统安全存储。此前被业务 403 误标 credentialInvalid 的设备点击正常“连接”：使用原 token 核验 identity 与完整快照，成功才清除误标；离线、真实撤销、过期或身份不符不清除、不重注册。真正撤销仍走已有明确重新授权入口。
5. 对照下方四项验收，再核对原任务、审批、结果、原生会话及 WSS 重连。已有执行继续由原设备核对，不跨设备重派未知轮次。确认后按原操作恢复接收。

生产升级必须由操作者在自己的维护流程中执行；本任务不执行生产部署或生产迁移。

## 四项人工验收

- **R1**：给 Host 发送未绑定资料引用。应看到“本轮失败／未启动”，原消息保留；再发合法纯文字，能够回应。修正绑定后点“修正后明确重试此输入”，双击或重连不得产生第二份重试。实际已启动而退出未知的输入仍显示核对，不自动重放。准备期间停止也不得迟到启动。
- **R2**：批准同初始 SHA 的 A→B 仓库计划。A 经真实检查／集成后，B 显示等待基线修订批准；独立任务及工具审批仍继续。打开原计划审阅，核对旧 SHA、新 SHA、原因和受影响的未分发任务；点击“将此准确提交加入待批准修订”，再批准。B 只从该 SHA 分发一次。A 的目标、Agent、基线、依赖和执行记录保持原样；不要用自然语言或本协议测试夹具代替实际 Git 检查。
- **R3**：B 端成果核验按钮应禁用并说明原协调设备负责；B 仍能提交和查看。用隔离测试直接发越权核验应 403/FORBIDDEN，但同 token 快照、重连和普通任务仍成功。真实过期、撤销和身份不匹配应 HTTP 401/AUTH_INVALID 或 WSS 4401；服务暂不可用不应伪装成凭证撤销。
- **R4**：从原 @ 候选选择中文／带空格成员，发送前改设备名，仍发往同 deviceId+Agent；原生目标保持确切 sessionId。离线、离会或编辑破坏绑定时明确提示且保留草稿，不能转 Host。删除整个 @ 后普通文字交 Host；复制的显示名需重新选择；邮件地址不受影响。多次同一目标可用，一条消息多个不同目标仍明确拒绝。

## 错误与恢复协议

业务 403 使用 detail={code:"FORBIDDEN",message:"..."}；认证失败为 401，detail.code="AUTH_INVALID"。Station 兼容旧字符串 403：用相同 token 查询无业务权限门槛的快照，仅其认证失败才将身份失效；网络不可达不等于认证失败。WSS 4401 只用于认证，1013 用于暂时不可用，4406 为不兼容协议。

Host preparing 表示尚未交给执行器；starting 为持久启动意图。启动前失败为 failed+exitConfirmed+notStarted，保留可读错误。message.retry 仅允许确认未启动的 Host 输入，并按原输入去重。对于旧 starting/reconcile 且没有 Guardian 启动记录的情况，原子建立不可再次启动的封存记录后才认定未启动；已有启动意图、未知执行或无法检查时保持核对，禁止自动执行第二次。

固定基线不变：依赖须全部在本会议通过核验，执行 SHA 必须匹配批准计划及会议 verifiedCommit。变更未分发任务的依赖基线必须明确审阅批准；已分发任务不可借修订改设备、Agent、基线或依赖。等待修订由持久计划和核验状态确定，重启不会重复制造提案。

## 回退

优先使用保留 .3 数据协议的兼容修订回退，关闭新接收与自动批准，继续保存和核对原执行。不要让 .2 客户端强行消费 .3 失败恢复状态，也不要通过删除新消息或重新注册设备来回退。

确需恢复升级前版本时，先维护并确认全部相关执行真实退出，保存升级后的增量记录和成果，再由操作者评估并恢复**同一时点**的备份及匹配旧版本。数据库备份恢复会影响备份后的共享元数据，不能在在途任务上盲目覆盖。无新增 DDL 不意味着可以忽略数据协议兼容性。

## 现场边界

自动回归使用本机生产 Hub 实现、独立 SQLite／MySQL 5.7、确定性执行夹具及隔离进程；UI 夹具明确标记无模型／无公网验收。两台物理 Windows、实际云托管发布、真实 GitHub PR／冲突、用户 Codex 桌面的串行接续和硬件功能仍需现场条件，不以这些夹具结果替代。
