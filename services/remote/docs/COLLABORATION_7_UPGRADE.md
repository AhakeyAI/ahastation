# collaboration.7：Host 拒绝收尾与准确成果门禁

本包必须与 `0.19.0-collaboration.7` Station 配套更新。没有生产部署操作；以下为运维交付说明。

## 数据与协议

- 延用 MySQL 5.7、schema2、原账号、设备、任务、收据和正文表；本次不增加表、字段或迁移。
- 从 .6 升级只更新程序。更早版本的正文表升级仍按 `COLLABORATION_6_UPGRADE.md`，不能跳过原备份与核验。
- `plan.propose` 在原请求成功收据查询之后、业务事务内明确拒绝时，错误详情附带原 `requestId` 和 `applied:false`。该事务回滚，原计划不变。旧成功收据优先返回，不会因为当前计划版本变化而被重新解释成失败。
- 请求身份冲突、连接换代、协议不兼容和网络未知不属于上述业务拒绝。Station 保留原请求；不重跑模型、不换身份重投。

## 恢复行为

Host 的原生退出证据和提案处理结果分别核对。原生执行确认结束且提案确定拒绝后，沿用原 `failed` 消息终态，显示“提案未应用”和具体原因，释放真实执行资源后可继续新输入。旧 `reconcile` 记录通过原 Guardian 完整结果和原请求身份恢复；已有拒绝证据不再次提交。缺少完整正文、退出证据或提交结果时继续核对。

同 attempt 已审阅／核验的准确成果不可改变，完全相同回执保持幂等。正文、报告和提交均属于既有 `delivery_hash` 身份。合法修改仍需明确范围修订／继续和新 attempt。待核验成果发生合法变化时撤销不匹配核验。

依赖创建、依赖链、执行基线修订、成果集成和最终验收均核对当前完成状态、退出证明、attempt、范围、报告和准确核验绑定。Hub 进行最终校验。重启不会清除这些规则或重写历史；旧错误组合即使保留 `integration=verified` 也不能放行。

旧错误组合不能通过重新 review 当前 D2 来继承原 D1 的 integration。Hub 明确拒绝不匹配的重新审阅，保留原证据；用户沿已有明确范围修订／继续／新 attempt 流程处理，依赖任务由原有新 attempt 逻辑同步要求重验，不自动重跑模型。

旧范围版本缺省为 0。缺少 `turnOutcome` 的旧记录仅在没有停止请求、具有退出证明和准确报告／核验绑定时沿用既有完成兼容规则；显式 unknown、failed、interrupted 不放行。缺少准确绑定的旧验收保留原验收事实，但不能据此授权新的依赖工作。旧预览不会补造为完整正文。

## 现场验收

在维护窗口备份后更新 Hub 与各 Station，保留原数据和凭据。使用专属会议复核：拒绝完整计划后的下一条输入、已核验后的不同成果拒绝、同成果重投、两端重启及明确新 attempt。真实双机、公网、GitHub 专属仓库与正常 Codex Desktop 双向接续仍需现场验收；本地 HTTP／隔离数据库不代替这些项目。
